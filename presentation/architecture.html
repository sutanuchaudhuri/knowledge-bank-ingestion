P0Pedagogical serving, not answer delivery

  1. Web /learnAnonymous problem selection, obstacle category and attempt input.
  2. REST boundaryFetch problem statement, skill metadata and eligible reviewed evidence.
  3. Draft generationGenerate a PENDING hint or micro-lesson from permitted context, without official answers or solutions.
  4. Progressive responseReveal only the requested hint level, from 1 through 3.
  5. Evidence-aware remediationPrefer reviewed prerequisites or easier same-skill practice; disclose missing evidence.
  6. Return promptAsk the learner to apply the small lesson to the original attempt.

Postgres owns pedagogical records and review status; Neo4j is a derived Skill-aware view. Projection inventories all PENDING, REVIEWED and REJECTED edge metadata. Atomic pedagogical-layer replacement protects the prior live layer on failure and applies review downgrades on success; the tutor separately uses reviewed evidence only. No direct database access is added to the agent. Schema/code implementation, Neon migration, Aura projection, content review, and app deployment are independent rollout gates. 1 · Crawl — two source-specific paths, one tracking table

PDF competitions (CHMMC, CMM, SMT, PUMaC, MPG_OLY): crawl_pdf_papers.py downloads the PDF, renders pages, and runs it through Docling to split into per-question markdown. AoPS wiki competitions (AMC10/AMC12/AIME): crawl_unmapped.py fetches the wiki page directly and parses problem/solution HTML. Every paper — regardless of source — ends up tracked in pipeline.pdf_source with a source_kind column (PDF | HTML) and starts life as PENDING the moment an admin registers its URL.

make crawl-unmapped LIMIT=200        # AoPS wiki
make crawl-pdf LIMIT=20 COMPETITION=SMT   # PDF archive

2 · Classify — model choice follows difficulty

AMC uses gpt-4o-mini (cheap, sufficient); AIME and the PDF-archive competitions use gpt-4o for stronger reasoning. The classifier proposes either an existing taxonomy concept or a brand-new one — new concepts get inserted on the fly, so the taxonomy grows with the corpus instead of needing to be hand-curated in advance.

Lesson learned the hard way: OpenAI enforces an org-wide tokens-per-minute (TPM) ceiling shared across every concurrent process. Running 7 parallel classification shards without retry/backoff produced 429 rate-limit errors; the fix was exponential backoff with jitter in the shared classifier module, plus deterministic sharding (--shard-index/--shard-count) so parallel workers never duplicate work.

make classify-pdf LIMIT=400 COMPETITION=SMT --shard-count 4 --shard-index 0

3 · Export — the bridge that almost didn't exist

Classification results lived only in local SQLite until an explicit export step was built to bridge them into the CSV corpus mirror that Postgres actually reads. Every export run does a pre- and post-write duplicate-key audit — it hard-fails if the run it just performed introduced a new duplicate key, so corruption is caught at write time, not discovered later in a query.

make export-classifications-dry   # preview only
make export-classifications       # writes + audits

4 · Load — idempotent upserts, honest counters

etl/load_corpus.py upserts every row on its natural key. An early version counted every row processed as "inserted" even when the database silently no-opped on conflict — fixed to use cursor.rowcount for an honest insert count. The whole run is now tracked as one row in pipeline.run (run_type='load_corpus'), so a crash mid-load shows up as a stuck RUNNING row instead of silent partial data.

make etl           # local Postgres
make etl-remote    # Neon (production)

5 · Project — Neo4j is never hand-edited

project_from_postgres.py reads core.*/knowledge.* read-only and issues Cypher MERGE for every node/edge — meaning the graph can be wiped and rebuilt from Postgres at any time with zero data loss. Every run is tracked in pipeline.graph_projection with node/edge counts, so a graph refresh is auditable exactly like a database load.

make project          # local Neo4j
make project-remote   # AuraDB (production)

6 · Embed — vector recalibration, also logged

Problem statements and solutions are chunked (max 6,000 chars) and embedded with text-embedding-3-small (1536-dim), stored in pgvector with HNSW indexing. Re-embedding is fully incremental — only chunks without an active embedding are processed — and now logged as an EMBED_BACKFILL row in pipeline.run, the same ledger as every other stage.

make vector-backfill LIMIT=500
make vector-index

Why "pre-filter" matters a real bug this architecture caught

The hybrid search originally ranked the global top-100 nearest-neighbor chunks first, then filtered by competition — so a competition filter on an under-represented competition could silently return zero rows even though matching problems existed. The fix: build an eligible_problem CTE from the filter before the ANN/lexical ranking, so filtering narrows the candidate set instead of post-filtering an already-ranked top-N. This is why the sequence diagram above explicitly calls out the pre-filter CTE — it's the load-bearing fix, not an implementation detail.

Why a concept-hierarchy bug made "combinatorics" searches look broken another real bug

knowledge.concept is a tree (HAS_SUBCONCEPT edges) — classification always tags the most specific leaf (e.g. count-subset), never the broad parent (count). A query for "combinatorics" measured against the literal count slug found almost nothing, even though the underlying search results were genuinely correct. Fixed with a recursive HAS_SUBCONCEPT closure query — P@10 for a representative case went from 0.00 → 0.30 after the fix, verified via the retrieval-evaluation harness below.

CHow retrieval quality itself is measured

Precision/Recall/MRR/nDCG@K against a derived golden query set (relevant = "any problem tagged with concept/technique X"), trended across runs in a flat CSV — because ground truth here is only as good as the classification step that produced it, this is treated as a diagnostic signal, not a hard gate.
