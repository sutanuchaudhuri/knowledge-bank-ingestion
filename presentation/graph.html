CCypher queries mapped to use cases

Use case: "Show me the knowledge graph around problem X" graph browser detail view 
MATCH (pr:Problem {canonical_code: $code})
OPTIONAL MATCH (pr)-[t:TESTS]->(c:Concept)
OPTIONAL MATCH (pr)-[u:USES_TECHNIQUE]->(tech:Technique)
OPTIONAL MATCH (pr)<-[:HAS_PROBLEM]-(p:Paper)<-[:HAS_PAPER]-(comp:Competition)
RETURN pr, collect(DISTINCT c) AS concepts, collect(DISTINCT tech) AS techniques, p, comp

Powers mathbank-web's /graph problem detail panel — one query, full context.

Use case: "What else tests the same concept?" related-practice recommendation 
MATCH (pr:Problem {canonical_code: $code})-[:TESTS]->(c:Concept)<-[:TESTS]-(related:Problem)
WHERE related.canonical_code <> $code
RETURN DISTINCT related.canonical_code, related.difficulty_band
ORDER BY related.difficulty_band
LIMIT 10

This is the Cypher-native equivalent of "find similar questions" — and it's what a personalization layer would filter by mastery score once MASTERED/STRUGGLES_WITH edges exist (see the dashed edges above).

Use case: concept prerequisite / gap detection planned — needs CONCEPT_RELATION traversal 
// Hypothetical once MASTERED edges exist:
MATCH (s:Student {canonical_id: $studentId})
MATCH (weak:Concept)<-[:STRUGGLES_WITH]-(s)
MATCH (weak)<-[:HAS_SUBCONCEPT]-(parent:Concept)
WHERE NOT (s)-[:MASTERED]->(parent)
RETURN parent.name AS prerequisite_gap, weak.name AS specific_weak_spot

Traverses the concept hierarchy (the same HAS_SUBCONCEPT tree that fixed the combinatorics search bug) to recommend prerequisite review, not just more of the same problem type.

Use case: coverage audit — which competitions are under-classified? operational, used in GOTCHAS #16 
MATCH (comp:Competition)-[:HAS_PAPER]->(:Paper)-[:HAS_PROBLEM]->(pr:Problem)
OPTIONAL MATCH (pr)-[:TESTS]->(:Concept)
WITH comp.name AS competition, count(DISTINCT pr) AS problems,
     count(DISTINCT pr) FILTER (WHERE EXISTS { (pr)-[:TESTS]->(:Concept) }) AS tagged
RETURN competition, problems, tagged, round(100.0 * tagged / problems, 1) AS pct_tagged
ORDER BY pct_tagged

This exact pattern (run against Postgres, not Cypher, for the production check) is what surfaced that SMT/CHMMC/PUMaC/CMM were 0-5% classified vs ~99% for AMC/AIME — directly motivating the parallel classification batches covered in the ingestion page.

DConstraints — what keeps the graph consistent

CREATE CONSTRAINT competition_id IF NOT EXISTS FOR (n:Competition) REQUIRE n.canonical_id IS UNIQUE
CREATE CONSTRAINT paper_id       IF NOT EXISTS FOR (n:Paper)       REQUIRE n.canonical_id IS UNIQUE
CREATE CONSTRAINT problem_id     IF NOT EXISTS FOR (n:Problem)     REQUIRE n.canonical_id IS UNIQUE
CREATE CONSTRAINT concept_id     IF NOT EXISTS FOR (n:Concept)     REQUIRE n.canonical_id IS UNIQUE
CREATE CONSTRAINT technique_id   IF NOT EXISTS FOR (n:Technique)   REQUIRE n.canonical_id IS UNIQUE
CREATE CONSTRAINT solution_id    IF NOT EXISTS FOR (n:Solution)    REQUIRE n.canonical_id IS UNIQUE

Every canonical_id is the Postgres UUID itself — the constraint is what makes MERGE-based re-projection safe to run an unlimited number of times.
