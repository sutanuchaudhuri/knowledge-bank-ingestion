P0 · Anonymous learning, evidence first

Help with the obstacle.
Then return to the problem.

A topic label tells us what a problem is about. A skill describes what the learner needs to do. The P0 workflow connects an expressed obstacle to a learning objective, requests an attempt, offers one hint at a time, and uses reviewed prerequisite or easier same-skill evidence when available. It does not require a student profile or pretend to know the learner's mastery.

AThe P0 learning loop

  1. LocateChoose a corpus problem and show its statement.
  2. DiagnoseSelect the obstacle; do not infer a permanent learner deficit.
  3. TryRequest the learner's attempt or explanation before giving help.
  4. ScaffoldReveal hint 1, 2, then 3 only on request; pause to try again.
  5. RemediateUse reviewed skill evidence, or label generated help PENDING.
  6. ReturnA return_prompt reconnects the lesson to the original attempt.

BFive obstacles, not five mastery scores

CategoryLearner signalTeaching response
concept“I don't understand the definition.”Clarify the idea with a small example; ask the learner to explain it back.
strategy“I don't know how to start.”Offer a direction or useful representation, not the completed solution.
execution“I know the method, but get stuck using it.”Isolate the next operation and check the learner's intermediate step.
calculation“My arithmetic or algebra keeps going wrong.”Check a local computation without exposing the final answer.
connection“I can't connect these ideas.”Bridge the relevant skills and return to the original relationship.

CTry the staged interaction

Illustrative · no API calls · not saved

Example obstacle: “I have a counting problem, but I am not sure my cases cover every possibility.”

Select an obstacle and share an attempt first. This prototype checks only that text is present; it does not grade it.

Each hint replaces the previous one. Selecting a different obstacle resets the sequence. A micro-lesson ends with a return prompt; it never claims your attempt is correct.

DEvidence and approval are different things

Reviewed corpus evidence

Eligible for prerequisite / easier-practice retrieval

The relevant skills, associations and prerequisite relations must carry reviewed evidence. “Easier” requires comparable reviewed required-level evidence for the same skill, not merely an earlier problem number, a difficulty estimate, or the same concept tag. No reviewed match means no invented recommendation.

Generated · PENDING

A helpful draft is not an approved fact

Generated hints and micro-lessons are marked PENDING and retain source/provenance and a return_prompt. They use the problem statement and permitted pedagogical context, not official answers or solutions as generation context. High confidence does not promote a generated record to REVIEWED.

Fail visibly: missing skill mappings, absent reviewed prerequisites, incomplete difficulty, or unavailable services should be reported as unavailable evidence. Neither this presentation nor an empty graph query establishes that a learning need has been resolved.

EWhat makes the graph pedagogical

ContractMeaning / guardrail
Skill / learning objective, optional level 1–5A stable identifier, unique slug, name and measurable objective. A level, when present, is an ordinal progression for the action to be learned, not a student mastery score or a universal difficulty scale.
(Skill)-[:PART_OF]->(Concept)Places an actionable objective inside a topic. A topic alone does not supply prerequisite evidence.
(prior:Skill)-[:PREREQUISITE_OF]->(dependent:Skill)Direction is prior → dependent. Retrieve prerequisites by following incoming edges to the dependent skill.
(child:Skill)-[:PART_OF]->(parent:Skill)Composition, not prerequisite ordering. Do not treat every part-of ancestor as a prerequisite.
(Problem)-[:REQUIRES|PRACTICES|TESTS]->(Skill)Separates prerequisites for solving, practice opportunities, and assessed objectives. Each association retains role, required_level (1–5), importance, confidence, source, and review_status.
Multidimensional difficulty + provenanceconceptual_depth, technical_load, algebraic_load, and insight_required are nullable levels 1–5. number_of_steps, prerequisite_depth, and estimated_contest_level retain provenance too. Missing means unknown, not zero; legacy difficulty_band is not complete pedagogical evidence.
PENDING / REVIEWED / REJECTEDDistinct review states on metadata. The graph inventories all three; only reviewed skills, edges and dimensions support tutor assertions. Confidence, import success and graph visibility do not approve a record.

E2One public contract, two clients

The anonymous web flow uses same-origin proxies; ADK tools call the same versioned REST service. Neither client accesses databases directly. Learning calls do not write learner attempts, mastery, or permanent profiles.

EndpointResponse / guardrail
GET /v1/tutor/learning-context/{problem_code}Statement, reviewed skills/prerequisites, difficulty, diagnostic choices and coverage warnings. No official answer or solution bodies.
GET /v1/tutor/prerequisites/{skill_slug}Bounded reviewed prerequisite traversal with depth, truncation and coverage semantics.
GET /v1/tutor/practice/{problem_code}Same-skill candidates called easier only when comparable reviewed required-level evidence supports the claim.
POST /v1/tutor/coachproblem_code, diagnosis, student_attempt, hint_level 1–3 → diagnostic question, micro-lesson, one hint, return prompt, provenance and warnings. Generated advice is PENDING.

Unknown problem / skill: 404. Invalid input: non-success validation response. Database, model and network failures: explicit errors, not empty successes. Full-solution browsing remains an intentional, separate action outside guided tutoring.
