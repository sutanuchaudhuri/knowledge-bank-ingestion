How this presentation was built

Written by the agent that built it, as a record of the actual decisions made — not a retrospective gloss. If you're evaluating whether to trust the content on the other six pages, this is the page that explains where it came from.

AThe brief

The request: a static HTML presentation, in the repo root, with clickable links, animation, an entity-relationship view that can be drilled into, real Neo4j graph content (not a mockup), Cypher queries mapped to concrete use cases, Postgres entity modelling, a student-impact framing for a non-technical audience, and — explicitly — a record of the thought process behind building it. That last requirement is this page.

BDecisions, and why

Why plain static HTML, not a framework

The repo already has a real Next.js app (mathbank-web) for the production UI. Introducing a second frontend framework just to show a presentation would mean a second node_modules, a second build step, and a second thing that can go out of date. A presentation's job is to be opened and read — .html files that work by double-clicking (or a one-line python3 -m http.server) serve that job better than a build pipeline would.

Trade-off accepted: no component reuse across pages, so the nav/footer markup is duplicated in all eight files. For eight static pages that's a non-issue; it would stop being one at twenty-plus pages, at which point a static-site generator would earn its keep.

Why a separate step-synced page for the tutor interaction, instead of one more static diagram

The ask was explicit: show what the student sees and what happens in the background, per interaction step, with the real REST/SQL/Cypher/vector-search detail at each one — a static sequence diagram (already on the inference page) compresses all of that into one picture read top-to-bottom. The tutor-interaction page keeps the same underlying facts but lets you hold one step still, read the actual SQL, then move to the next — autoplay exists for a passive walkthrough, step/dot navigation exists for stopping on the one step you actually want to study.

The chat panel is explicitly labeled "illustrative mock" in its own header — the brief noted the real UI will keep changing, so the page commits to keeping the system sequence accurate and deliberately doesn't try to pixel-match mathbank-web's actual chat component.

Turn 2 (mastery) mixes real and planned steps on purpose, with a visible LIVE / PLANNED / LIVE + PLANNED badge per step — the same honesty convention as every other page, applied at step granularity instead of page granularity.

Why Mermaid for diagrams, vis-network for the graph, no other dependencies

Mermaid was already the house style — every requirements doc in this repo (requirements/09_PIPELINE_SEQUENCE.md, 10_*, 11_*) already has Mermaid flowcharts and sequence diagrams written during earlier work. Reusing that syntax here means the diagrams in this presentation and the diagrams in the markdown docs are the same source language — several were copied near-verbatim rather than redrawn.

vis-network was chosen for the one interactive element (the live graph canvas on graph.html) specifically because it accepts plain {id, label, group} node objects and {from, to, label} edge objects — no schema translation needed between "what Neo4j returns" and "what the renderer wants" beyond a thin mapping function in assets/app.js.

Both are loaded from CDN (cdn.jsdelivr.net, unpkg.com) rather than vendored into the repo — this presentation needs network access to render diagrams. That's a real limitation, documented here rather than silently assumed.

Why the graph data is a real export, not hand-written JSON

The brief explicitly asked for "actual neo4j graphs," so a hand-authored sample graph would have defeated the point. The data in assets/data/graph-sample.json was produced by a one-off Python script run against the live AuraDB instance:

MATCH (comp:Competition {external_code:'AMC10'})-[:HAS_PAPER]->(p:Paper)
WHERE p.year >= 2023
WITH comp, p LIMIT 2
MATCH (p)-[:HAS_PROBLEM]->(pr:Problem)
WITH comp, p, pr LIMIT 14
OPTIONAL MATCH (pr)-[t:TESTS]->(c:Concept)
OPTIONAL MATCH (pr)-[u:USES_TECHNIQUE]->(tech:Technique)
RETURN comp, p, pr, collect(...) AS concepts, collect(...) AS techniques

43 nodes, 65 edges — small enough to render cleanly in a force-directed layout, large enough to show the real shape of the TESTS/USES_TECHNIQUE fan-out per problem. The export script itself was a throwaway (/tmp/export_graph_sample.py), not added to the permanent codebase, since its only job was producing this one static asset.

Why every number and bug story is sourced from the actual codebase

Before writing a line of HTML, the exact current schema (all 5 Postgres schemas, every table and column), the exact Neo4j node/relationship model, the exact REST endpoint list, and the exact Mermaid diagrams already written in requirements/ were pulled fresh from the live files — not recalled from memory of earlier work in this session. The two "bug stories" on the inference page (the pre-filter fix, the concept-hierarchy fix) are both real incidents with real before/after precision numbers, documented in this repo's GOTCHAS.md (#15 and #16) — nothing in those callouts is invented for narrative effect.

Why an audience toggle instead of two separate presentations

The brief asked for one presentation that serves both a technical and a business audience. Two separate documents would drift apart over time (the classic problem with "the deck" vs "the eng doc"). A single source of content with a CSS/JS toggle ([data-audience-only], persisted in localStorage) keeps one set of facts and only varies the framing — visible on the overview and inside the use-case accordions.

Turn 3 went from mockup to real implementation (Round 11) — the decision trail

Turn 3's scaffolded problem-decomposition was deliberately the most speculative scenario on the interaction page — mostly planned badges, by design, since nothing behind it existed yet. When asked to turn it into a real feature, the build order was chosen to de-risk the most uncertain part last:

  1. Hint-weighted mastery first (MST-09). learner.attempt.hint_count already existed in the schema and was already flowing through POST /v1/learner/attempts — it just wasn't read by mastery.py. Closing this gap required no new infrastructure, only a new pure function (hint_penalty(hint_count) = max(0.4, 1/(1+0.25*hint_count))) wired into the existing scoring loop, kept backward-compatible via .get("hint_count", 0) so neither older callers nor existing tests needed to change.
  2. Then the OpenAI-backed decomposition/grading endpoints (AGT-11). mathbank_rest/tutor.py follows the exact client-setup pattern already established by db/vector_search.py for embeddings (load_dotenv(), an explicit OPENAI_API_KEY presence check, a module-level OpenAI() client) — deliberately not a new architectural pattern, just the chat-completions sibling of a pattern already proven in this codebase. The decomposition prompt explicitly forbids revealing the final answer; the grading prompt is told to judge reasoning, not pattern-match a number.
  3. Then the agent tools. decompose_problem/check_subproblem_answer were added to rest_tools.py using the same typed-callable-with-docstring convention as the other six tools (ADK reads the docstring as the tool description), and the agent's INSTRUCTION was extended to tell it to present one subproblem at a time and never reveal the official answer mid-walkthrough.

Every claim above was verified, not assumed: 32/32 pytest passing in mathbank-rest (12 of them new), a live curl against the real corpus that decomposed AIME_1992_Q06 into 3 genuine subproblems, and a live grading call that correctly marked a wrong student answer (9) as incorrect against the true count (21) with substantive feedback — evidence the grader checks the math rather than rubber-stamping. The agent module was also loaded directly to confirm all 8 tools register cleanly. Full trail in mathematics_tutor_db_plan/00_implementation_progress.md (Round 11) and requirements/10_AGENTIC_TUTOR_AND_STUDENT_MASTERY_REQUIREMENTS.md (AGT-11, MST-09, §5.3 sequence diagram). What's still honestly incomplete and said so on the interaction page: hints aren't logged per-subproblem (no core.subproblem table), and the "detect a weak subskill, then route to easier practice" hand-off relies on the agent's own reasoning rather than a scripted pipeline.

Known limitations, stated plainly
  • Requires network access at view time (Mermaid/vis-network/MathJax load from CDN).
  • fetch() of the local graph-sample.json is blocked by browsers under a bare file:// URL in some configurations — serve the presentation/ folder with any static file server (e.g. python3 -m http.server) if the graph canvas shows an error instead of nodes.
  • The live graph export is a snapshot (AMC10 2023, 14 problems) taken on 2026-10-04 — it will not reflect classification work that lands after that date. It's representative, not live-streaming.
  • Nav/footer markup is duplicated per page by design (see above) — a deliberate, bounded trade-off.
