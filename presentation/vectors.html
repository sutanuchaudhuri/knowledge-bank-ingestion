03b · Vectors

Vector Models (pgvector in Postgres)

Every problem, solution, solution step, learning item and taxonomy node is rendered as a short, labelled text and embedded with OpenAI text-embedding-3-small. The vectors live in Postgres next to the rows they describe, so one SQL statement can apply hard filters (skill, subconcept, publication status) and then rank by meaning. Vectors find "problems like this one" when the words differ; the knowledge graph explains why they are related; full-text search catches exact terms. Search fuses all three.

BFrom a row to a vector

Text is never embedded straight from a source column. It is first rendered into a representation with a kind prefix (so a step and a problem with similar words stay distinguishable), hashed, split into chunks, and only then embedded. If the content hash is unchanged, no new embedding is requested.

flowchart LR

    SRC -->|"render + kind prefix"| REP["search.representation (rendered_text, content_hash, ACTIVE)"]
    REP -->|"hash changed"| OLD["previous representation marked SUPERSEDED"]
    REP -->|"split at 6,000 chars"| CH["search.chunk (FULL or WINDOW, textsearch tsvector, owner ids)"]
    CH --> JOB["search.embedding_job (input_hash, attempts, heartbeat)"]
    JOB -->|"OpenAI batch of 100"| EMB["search.embedding (vector 1536, ACTIVE)"]
    MODEL["search.embedding_model (openai, text-embedding-3-small, v1, 1536, COSINE)"] --> EMB
    EMB --> HNSW["HNSW index: cosine ops, partial on active model"]
    CH --> GIN["GIN full-text and trigram indexes"]

UNIQUE(chunk_id, embedding_model_id) allows one vector per chunk per model, so a second model can be added side by side. The vector column has no fixed dimension; the HNSW index casts to vector(1536) and is partial on the active model id. The chunk_single_pedagogy_owner CHECK makes a chunk belong to at most one step, item or taxonomy node.

Why two item vectors?

The question vector matches wording ("draw a line through P"). The signature vector matches pedagogy ("a first-move subproblem on auxiliary construction"), even when two items share no words.

Why neighbours in taxonomy text?

A bare name such as "The radical axis" is too short to embed well. Listing the parent path, skills and techniques (max 15 each, then "and N more") gives the vector a context. Boilerplate descriptions are filtered out.

Why the kind prefix?

[Problem], [Solution step] and [Learning item] keep different units apart in vector space, and the eligible CTE re-checks rendered_text so a stale vector cannot match an edited problem.

EModel, index and idempotency

ModelOpenAI text-embedding-3-small, revision v1, 1536 dims, cosine; registered in search.embedding_model with status ACTIVE.
ANN indexidx_search_embedding_text_embedding_3_small_hnsw: USING hnsw ((embedding::vector(1536)) vector_cosine_ops) WHERE embedding_model_id = '<active>' AND status = 'ACTIVE'.
ChunkingUp to 6,000 characters → one FULL chunk; longer text splits at paragraph boundaries into WINDOW chunks. Search takes the minimum distance per entity.
Idempotencycontent_hash on the representation, input_hash on the job. Re-running with unchanged content makes no new embeddings and costs nothing.
EligibilitySteps must be PUBLISHED; items APPROVED, student-visible and no-proof. Anything that stops being eligible has its representation SUPERSEDED.
Step identityTextbook keys are text, so a deterministic uuid5 surrogate is the representation's source_entity_id; the real key sits in the chunk's owner column.

1 · Problem search: semantic + lexical RRF live · db/vector_search.py search_problems 
WITH eligible_problem AS (          -- filters BEFORE ranking
  SELECT p.problem_id, regexp_replace('[Problem] ' || p.statement_text,'[[:space:]]+$','') AS rendered
  FROM core.problem p JOIN core.paper pa ... JOIN core.competition comp ...
  WHERE TRUE AND comp.external_code = :competition AND ed.year >= :year_min
), semantic AS (
  SELECT e.chunk_id, row_number() OVER (ORDER BY e.embedding::vector(1536) <=> CAST(:query_vector AS vector(1536))) AS rnk
  FROM search.embedding e JOIN search.chunk c ... JOIN search.representation r ...
  JOIN eligible_problem ep ON ep.problem_id = c.problem_id
  WHERE e.embedding_model_id = :model_id AND e.status = 'ACTIVE'
    AND r.status = 'ACTIVE' AND r.representation_kind = 'PROBLEM_STATEMENT'
    AND r.rendered_text = ep.rendered
  ORDER BY ... LIMIT :candidate_limit
), lexical AS (
  SELECT c.chunk_id, row_number() OVER (ORDER BY ts_rank_cd(c.textsearch, websearch_to_tsquery('english', :query_text)) DESC) AS rnk
  ...
)
-- FULL OUTER JOIN semantic/lexical, score = 1/(60+semantic_rnk) + 1/(60+lexical_rnk)

Why filter first: ranking the global top-N and then filtering by competition silently returned zero rows for small competitions whose problems were not among the nearest neighbours. order_by can be relevance, year_desc ("recent problems on …") or year_asc.

2 · Three-way fusion with the graph live · db/hybrid_search.py fuse → POST /v1/search/problems

The vector query returns up to min(max(limit×4, 100), 400) candidates. The top 25 semantic hits become seeds for the graph leg. Each source contributes 1/(60 + rank):

4 · Filtered step search: exact distance over a small candidate set live · db/step_search.py build_search_sql 
WITH eligible AS (
  SELECT c.chunk_id, c.solution_step_id AS entity_id, c.textsearch
    FROM search.chunk c
    JOIN search.representation r ON r.representation_id = c.representation_id
    JOIN search.preprocessing_profile pp ON pp.preprocessing_profile_id = r.preprocessing_profile_id
    JOIN pedagogy.solution_step s ON s.solution_step_id = c.solution_step_id AND s.publication_status = 'PUBLISHED'
   WHERE r.status = 'ACTIVE' AND pp.name = 'pedagogy_step_v2'
     AND r.representation_kind = ANY(:kinds)
     AND c.subconcept_node_id = :subconcept_node_id      -- e.g. 'GEO.C03.S10'
     AND s.is_checkpoint = :is_checkpoint
     AND EXISTS (SELECT 1 FROM pedagogy.solution_step_technique t
                 WHERE t.solution_step_id = s.solution_step_id
                   AND t.technique_node_id = :technique_node_id AND t.review_status = 'APPROVED')
), semantic AS (
  SELECT el.entity_id, min(e.embedding <=> CAST(:query_vector AS vector)) AS distance
    FROM eligible el JOIN search.embedding e ON e.chunk_id = el.chunk_id
   WHERE e.embedding_model_id = :model_id AND e.status = 'ACTIVE' GROUP BY el.entity_id
) ...

Only allow-listed filter names are accepted (unknown names raise); all values are bound parameters. Ten step filters: skill, subconcept, concept, step_type, tutor_role, is_checkpoint, problem, exclude_problem, max_hint_level, technique.

10 · Adding a second model without downtime illustrative procedure
  1. Register a new search.embedding_model row (status REGISTERED, its own dimensions).
  2. Backfill: new search.embedding rows for the same chunks (UNIQUE per chunk + model).
  3. Create a partial HNSW index cast to the new dimension for that model id.
  4. Flip the ACTIVE status and point EMBEDDING_MODEL_NAME at the new model. _active_model_id() is cached per process (lru_cache), so restart REST afterwards. The old vectors stay for rollback.

This is why the vector column is deliberately unconstrained.

11 · Inspect the nearest steps to one step illustrative read-only SQL 
WITH q AS (
  SELECT e.embedding AS v FROM search.chunk c JOIN search.embedding e USING (chunk_id)
   WHERE c.solution_step_id = 'PRASOLOV_PGV1/STEP-3.50-MAIN-02' AND e.status = 'ACTIVE' LIMIT 1)
SELECT c.solution_step_id, c.skill_node_id, e.embedding <=> q.v AS distance
  FROM q, search.chunk c JOIN search.embedding e USING (chunk_id)
 WHERE c.solution_step_id IS NOT NULL AND e.status = 'ACTIVE'
 ORDER BY distance LIMIT 10;

Useful for checking whether the skill labels and the vectors agree: the neighbours of a similarity step should be other similarity steps.

GWhy exact distance after filters, not HNSW

HNSW (approximate)

Fast over the whole table, but it returns the top-N nearest first. A filter applied afterwards (e.g. one subconcept, PUBLISHED only) can drop most or all of them, so filtered searches silently return too few rows.

Filter, then exact

Step and item search narrow to the eligible chunks first (often a few hundred), then compute exact <=> over that set. It is always correct and fast enough at this size. HNSW serves the unfiltered problem search path.

HAnswer-leak and visibility safety

  • Solution and step vectors are used to rank; step text is stripped from results unless the caller opts in.
  • Similar-step practice excludes the origin problem.
  • Learning items are re-checked against the live row after ranking; a stale vector cannot surface unpublished content.
  • Problem search re-compares rendered_text with the current statement, so an edited problem's old vector is ignored.
  • Student answers are never embedded. A free-text search query is embedded on the fly to rank results, and that vector is not stored.

IWhere vectors are not used

Gap diagnosis

Deterministic rules over the step DAG and taxonomy columns. The result is explainable and reproducible.

Recovery ranking

Skill match, then subconcept (2) / concept (1), then variety. The learning-item vector search is ready but not wired in.

Mastery and grading

Mastery comes from attempt evidence. Grading compares against the reference; similarity is never treated as correctness.

JGotchas

Filter after ANNReturned zero results for small competitions. Fixed by filtering in the eligible CTE before ranking.
Short text embeds poorlyTaxonomy names alone were too thin; neighbour context was added, capped at 15 per list.
Text ids vs uuid columnsTextbook keys are text; a uuid5 surrogate fills source_entity_id.
Paid backfillsEvery embedding target is labelled paid in the Makefile; status targets are read-only and free.
Query embedding costFree-text search makes one embedding call per query. Step practice reuses stored vectors to avoid it.
Cached model id_active_model_id() is lru_cached per REST process. Newly embedded rows are visible immediately, but a model switch needs a REST restart.
