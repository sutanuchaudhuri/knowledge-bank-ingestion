## 1. Executive summary — the one root mechanism behind almost everything

Doc 50 found that `Misconception`/`Claim`/`TheoryItem`/`LearningItem`(diagnostic) nodes are generated **one per route checkpoint**, not drawn from a reusable catalog. This document traces that one level deeper, into Postgres, and finds the exact mechanism and its blast radius:

- **`knowledge.misconception` — the intended curated catalog table — has 0 rows.** It is fully designed (symptom/why_wrong/correct_model/severity/review_status columns all exist) but **entirely unused**.
- The real content lives in **`pedagogy.route_asset`**, written by [route_enrichment.py](/Volumes/External/Developer/knowledge-bank-ingestion/mathbank-rest/src/mathbank_rest/route_enrichment.py)'s `attach_enrichment()`, which calls an LLM **once per route checkpoint** and stores the result as a freestanding JSON blob — with **no deduplication, no canonicalization, and no write-back to `knowledge.misconception`** at all.
- Confirmed counts: 80,242 `MISCONCEPTION` / 80,494 `CLAIM` / 80,239 `THEORY` / 80,256 `LEARNING_ITEM` (diagnostic) rows in `pedagogy.route_asset` — these are exactly the four node types that were 80,168-flat in doc 50's Neo4j inventory.
- **The good news, confirmed live:** `content->'taxonomy_node_ids'` is **already populated on 99.2% of MISCONCEPTION rows** (79,591 of 80,242) at write time — the graph projector in doc 50 derived this transitively through `RouteStep` as a workaround; it didn't need to — **the direct link was sitting in Postgres the whole time**, just never read by the projector.
- **Deduplication opportunity, confirmed live:** 12.7% of MISCONCEPTION rows (10,224 of 80,242) are **byte-for-byte identical** in their `description` text to another row — a zero-risk, zero-new-infrastructure merge opportunity, available today.
- **pgvector is already installed** (v0.8.6) with two existing embedding tables (`search.embedding`, `artifact_runtime.artifact_embedding`, both 1536-dim) — real semantic clustering of the remaining near-duplicates is infrastructure-ready, not a new capability to build from scratch.
- A **second, parallel, mostly-disconnected taxonomy system** (`pedagogy.taxonomy_node`, 6,968 rows) coexists with the curated `knowledge.*` tables (885 concepts / 279 techniques / 2,997 skills) — the majority of `taxonomy_node` rows have no link back to a curated entry at all (confirmed: only 202 of 3,413 `SKILL`-type nodes link to a real `knowledge.skill` row).

### 3.1 Within the auto-generated taxonomy, two *opposite* information-loss mechanisms coexist

Live follow-up investigation (triggered by a user observation that "concentration" might reflect missing node-to-node similarity): **897 of the 6,968 `pedagogy.taxonomy_node` rows are fixed, curriculum-category "bucket" codes** (e.g. `GEO.C04.AREA`, matching the pattern `[A-Z]+\.C\d+\.[A-Z_]+` — 353 Concept / 303 Skill / 218 Technique / 23 Subconcept codes), not per-instance UUIDs. These are a *real, intentional* coarse-grained curriculum taxonomy — confirmed by example: `GEO.C04.AREA` (named "Calculating Area of Triangle BPC" — misleadingly specific, see below) legitimately aggregates 2,342 `solution_step_requirement` rows, because "calculate an area" genuinely recurs that often across the corpus. **This is correct, by-design concentration, not a bug** — directly analogous to `knowledge.concept`'s "Algebra" legitimately having 4,708 `TESTS` edges (§4's "requires-skill"/"tests" row).

But this reveals the **opposite** problem from §1's misconception over-fragmentation:

- **The bucket node's own display name is stale/misleading.** `GEO.C04.AREA`'s name — "Calculating Area of Triangle BPC" — is just whichever specific instance happened to populate it *first*; of the 2,342 rows that resolve to this code, only 4 ever proposed a distinct, non-blank `proposed_name` (confirmed: `"Area of a Square"`, `"Calculating Area of Triangle BPC"`, `"Calculating Area of a Square"`, `"Calculating Area of a Triangle"`, each used exactly once) — **2,338 of 2,342 (99.8%) have a blank `proposed_name`/`proposed_description` entirely.** The node never gets re-labeled to reflect what it actually serves as (a generic area-calculation category), so it visually reads as hyper-specific while functioning as a broad bucket.
- **The fine-grained, per-instance distinguishing signal that *does* exist is inert.** Corpus-wide, only 13,502 of 82,023 `solution_step_requirement` rows (16.5%) carry any `proposed_name` at all; the other 83.5% resolve straight to the coarse bucket code with zero recorded distinction. Even the 16.5% that *do* have one (e.g. "area of a triangle via Heron's formula" vs. "area of a square" — genuinely different pedagogical content, both bucketed under the same `GEO.C04.AREA`) are **never embedded, linked, or surfaced at tutoring-query time** — it is dead data sitting in a column, not a retrievable signal. This is precisely the user's concern: *"the tutor during querying need[s] to get that data to understand concepts/misconceptions,"* and today it structurally cannot, even where the data already exists.

So the full picture is two distinct, independently-confirmed gaps, not one:
1. **Process-layer over-fragmentation** (Misconception/Claim/Theory/diagnostic-LearningItem, §1): every instance is unique, near-duplicates never merged — needs ENR-1/ENR-2's dedup+embedding clustering.
2. **Taxonomy-layer signal loss** (Concept/Skill/Technique requirement bucketing, this section): correctly coarse by design, but (a) stale bucket display names, and (b) the finer per-instance signal that *is* captured is never embedded or exposed to tutoring queries — needs the new **ENR-8** below.

### ENR-8 — Surface the fine-grained per-instance requirement signal within each taxonomy bucket — 🟡 ITEM 1 IMPLEMENTED, item 2 not yet

1. **Cheap, immediate:** regenerate each fixed-code bucket node's display `name`/`description` from an aggregate of what it actually contains (e.g. the code's own curriculum-category label, "Area calculation techniques (Geometry Ch. 4)"), not the first-ever `proposed_name` that happened to populate it — fixes the stale/misleading-label half of this finding without touching retrieval.

   **✅ IMPLEMENTED, live-verified** (deviated from the literal "decode a curriculum-category label" idea above — confirmed live that the domain-prefix scheme is too ad hoc, 70+ inconsistent prefixes, to decode reliably): [scripts/relabel_taxonomy_buckets.py](/Volumes/External/Developer/knowledge-bank-ingestion/mathbank-rest/scripts/relabel_taxonomy_buckets.py) instead appends a purely factual, auditable suffix — the real usage count and (when more than one distinct proposal was ever recorded) the list of them — to every fixed-code node used ≥10 times. Applied to all 127 qualifying nodes; e.g. `GEO.C04.AREA` now reads *"Calculating Area of Triangle BPC (recurring category, 2,342 uses; includes: Area of a Square, Calculating Area of Triangle BPC, Calculating Area of a Square, Calculating Area of a Triangle)"* — no longer silently misleading about being one hyper-specific instance. Idempotent (strips and reapplies its own suffix format on re-run). Propagated into Neo4j via a full `route_projection.project()` re-run and live-confirmed: `MATCH (n) WHERE n.name CONTAINS "recurring category" RETURN count(n)` returns **127** (all of them, all labeled `Technique`), matching the Postgres write exactly.
2. **The retrieval fix the user is actually asking for:** embed the 13,502 non-blank `proposed_name`/`proposed_description` rows (reusing ENR-2's pgvector infrastructure) and expose them as a **second-stage ranking step scoped within the already-graph-traversed bucket** — e.g. the tutor's existing graph traversal narrows to "this step requires `GEO.C04.AREA`," then a pgvector similarity query ranks that bucket's embedded instances against the *current* problem's own step context, surfacing "area of a triangle" ahead of "area of a square" when that's what's actually relevant. This is the same two-query pattern (Postgres pgvector for ranking → graph traversal for structure) already recommended in ENR-2's "why not Neo4j vector indexes" note — confirms that decision rather than reopening it.

   ⏳ **NOT IMPLEMENTED** — needs ENR-2's embedding infrastructure first.
3. **Do not** attempt to split each bucket into many fine-grained sub-nodes outright — 83.5% of rows have no distinguishing signal to split on at all, and the 897-code curriculum structure is itself a reasonable, intentional granularity for the *graph* layer; the fix belongs at the *retrieval* layer (embedding-ranked, not graph-structural).


This is why Neo4j's node counts (2,936 Concept, 1,484 Technique, 6,208 Skill) are larger than the curated Postgres counts — the graph merges both systems, but most of the auto-generated half was never reconciled against the curated half. Every misconception/theory/claim generated by the route pipeline links into the **auto-generated** half (`taxonomy_node_id`), compounding the disconnect.

## 5. Concrete enrichment proposals (ENR-*)

### ENR-1 — Make `knowledge.misconception` the real catalog it was designed to be — 🟡 PHASE A IMPLEMENTED (Postgres + Neo4j), Phase B not yet

1. **Phase A (free, zero risk):** merge the 10,224 exact-duplicate-description `MISCONCEPTION` rows into shared canonical entries. Confirmed live: of the 4,941 duplicate-description groups (15,165 rows), 1,340 groups (27%) already share identical `taxonomy_node_ids` across every member (trivial, single-target merge); the remaining 73% have members pointing at *different* taxonomy targets for identical description text — which is not a conflict, it means the same misconception genuinely recurs across multiple skills/concepts, so the merge target should support **multiple** taxonomy links per canonical misconception (a junction table, not a single FK column — see below).

   **✅ IMPLEMENTED, live-verified**: migration [039_misconception_catalog.sql](/Volumes/External/Developer/knowledge-bank-ingestion/mathbank-db/sql/039_misconception_catalog.sql) + [scripts/backfill_misconception_catalog.py](/Volumes/External/Developer/knowledge-bank-ingestion/mathbank-rest/scripts/backfill_misconception_catalog.py) applied live. 80,242 MISCONCEPTION rows deduplicated by exact `description` text into **70,018** canonical `knowledge.misconception` rows (12.7% reduction). A real schema correction happened mid-implementation: the original design added `canonical_misconception_id` directly onto `pedagogy.route_asset`, but live testing hit `pedagogy.guard_route_snapshot()` — confirmed this trigger blocks ANY write to a route_asset row once its release leaves DRAFT status, which almost all existing rows already have. Fixed by using a separate, purely additive `knowledge.route_asset_misconception_link` side table instead (never touches the guarded table). A second, unrelated performance problem was also hit and fixed: the first one-row-at-a-time implementation was projected to take 4+ hours (confirmed: ~4 min per 1,000 groups); rewritten to use deterministic client-side `uuid5` ids (no `RETURNING` round trip needed) and multi-row bulk `INSERT ... VALUES (...), (...), ...` statements, which completed the full 70,018-group run in under 90 seconds.
2. **Phase B (needs ENR-2's embeddings):** cluster the remaining ~70,018 distinct-but-often-related descriptions by semantic similarity, not just exact text, to find near-duplicates ("Misapplication of Pythagorean theorem" vs. "Misunderstanding Pythagorean theorem application" — a real pair confirmed live in the current data).

   ⏳ **NOT IMPLEMENTED** — needs ENR-2's embedding infrastructure first.
3. Schema: populate `knowledge.misconception` from the resulting canonical set; add a many-to-many `knowledge.misconception_taxonomy_link (misconception_id, target_type, target_id)` junction table (not a single nullable FK) to honor the confirmed multi-target reality; add `pedagogy.route_asset.canonical_misconception_id` so each per-checkpoint row still resolves to its canonical entity without losing the original per-checkpoint generated text.

   **✅ IMPLEMENTED** (with the side-table correction noted above): `knowledge.misconception_taxonomy_link` populated with 78,781 rows (keyed on `taxonomy_node_id`, not a generic `target_type`/`target_id` pair — simpler, matches the confirmed reality that the overwhelming majority of real taxonomy links live in `pedagogy.taxonomy_node`, not the curated `knowledge.*` tables); `knowledge.route_asset_misconception_link` populated with 80,242 rows (100% of MISCONCEPTION rows linked).

### ENR-2 — Reuse the existing pgvector infrastructure for semantic clustering — ✅ IMPLEMENTED, live-verified

- pgvector is already installed (v0.8.6); `search.embedding` and `artifact_runtime.artifact_embedding` already establish the project's embedding convention (1536-dim, a dedicated table with `embedding_model_id` provenance, not an inline column on the content table).
- Add `knowledge.misconception_embedding` / `knowledge.skill_embedding` following that exact same pattern, embedding `description`/`symptom`/`why_wrong` (misconception) and `objective` (skill).
- Enables real community detection (Neo4j GDS `louvain`/`labelPropagation` over a similarity-threshold graph, or plain k-means in Postgres via pgvector's `<->` operator) — the direct technical answer to the original "cluster skills/misconceptions" ask.

**✅ IMPLEMENTED, live-verified — the direct, explicit fix for "no similarity search happening in the graph at all":** migration [040_similarity_embeddings.sql](/Volumes/External/Developer/knowledge-bank-ingestion/mathbank-db/sql/040_similarity_embeddings.sql) + [041_similarity_embeddings_hnsw_index.sql](/Volumes/External/Developer/knowledge-bank-ingestion/mathbank-db/sql/041_similarity_embeddings_hnsw_index.sql) add `knowledge.misconception_embedding` and `pedagogy.taxonomy_node_embedding` (covering Concept/Skill/Technique/Subconcept uniformly — confirmed live this is the actual dominant source of graph taxonomy nodes, not just the curated `knowledge.concept/skill/technique` tables, since most Neo4j taxonomy nodes are auto-generated: 6,968 `pedagogy.taxonomy_node` rows vs. 4,161 curated rows). [scripts/generate_similarity_embeddings.py](/Volumes/External/Developer/knowledge-bank-ingestion/mathbank-rest/scripts/generate_similarity_embeddings.py) generates embeddings via batched OpenAI calls (up to 500 texts/call, confirmed live at ~500/1.4s — the project's existing single-string-per-call `_openai_embedding()` helper would have needed ~77,000 HTTP round trips) and precomputes top-8 nearest-neighbor pairs (cosine similarity ≥ 0.80) using an HNSW-index-assisted `LATERAL` join (a naive full self-join over 70,018 misconceptions would be ~4.9 billion pairs — confirmed impractical without an index; the first migration version used a flexible unconstrained `vector` column matching `artifact_embedding`'s precedent, which turned out not to support ANN indexing, corrected in 041 to a fixed `vector(1536)` column + HNSW index).

Applied live: **70,018** misconception embeddings, **6,968** taxonomy-node embeddings (~24.6 minutes total, dominated by Postgres insert round trips, not the embedding API itself), **300,404** misconception similarity pairs, **9,386** taxonomy-node similarity pairs (scoped same-`node_type`-only — comparing a Concept's embedding against a Skill's is not a meaningful "similar" signal even if the vectors happen to be close). Spot-checked quality live: top misconception pairs include genuine semantic near-duplicates with different wording ("Students may confuse combinations with permutations, leading to incorr..." / "...or miscalculate th..." at 0.974 similarity) — exactly the near-duplicate-but-not-exact-text case ENR-1 Phase A's dedup couldn't catch. Technique pairs surfaced several **exact-name duplicate nodes at similarity 1.0** ("Power of a Point" / "Power of a Point", "Binary Subtraction" / "Binary Subtraction") — a real, additional confirmation of the auto-generated-taxonomy-duplication finding from ENR-8's root-cause analysis, now directly actionable as a future consolidation target (not pursued in this pass).

Projected as `SIMILAR_TO` edges directly inside `route_projection.py` (not a separate companion script, per the BUG-5/[GOTCHAS.md §24](/Volumes/External/Developer/knowledge-bank-ingestion/documentation/GOTCHAS.md) lesson), scoped to node ids guaranteed to already exist in the graph (curated taxonomy nodes, or auto-generated ones already referenced elsewhere in the current run — never introduces an isolated node whose only edge is a similarity link). Four new `graphConfig.js` tabs: `misconception-similar` (300,013 edges live), `concept-similar` (1,704), `skill-similar` (6,512), `technique-similar` (1,170) — all four confirmed live via direct Neo4j query and screenshotted (`technique-similar` in particular shows real, visually clear k-NN cluster structure, not a disconnected-dust pattern: [after/technique-similar.png](/Volumes/External/Developer/knowledge-bank-ingestion/documentation/requirements/assets/51_misconception_canonicalization/after/technique-similar.png)).

**A second production incident was hit and fixed during this rollout:** the live re-projection run initially failed with `Neo.TransientError.General.MemoryPoolOutOfMemoryError` on the bulk relationship-DELETE step — a previously-documented, anticipated failure mode (GOTCHAS.md §23) that the new `SIMILAR_TO` edges pushed past (total edge count 1.55M, well over the ~1M threshold). Confirmed this specific failure rolls back cleanly (node/edge counts unchanged, verified live) before fixing the actual root cause: the single unbatched `DELETE`/`DETACH DELETE` statements were rewritten to use Neo4j 5's native `CALL (...) { ... } IN TRANSACTIONS OF N ROWS` batched-subquery construct (same pattern already used elsewhere in this codebase), which commits per-batch internally and fits the same memory budget as the already-batched node/edge writes. Re-run succeeded: `pipeline.graph_projection` status `COMPLETED`, 415,682 nodes / 1,551,106 edges.

**Why not Neo4j-native vector indexes for the live ANN search path itself (still holds, decision unchanged):** Neo4j Aura offers a
["vector-optimized configuration"](https://neo4j.com/docs/aura/managing-instances/vector-optimization/)
that reallocates instance memory toward vector indexes. Checked live: `SHOW INDEXES` on the
current instance returns zero `VECTOR`-type indexes — there is nothing to optimize for today,
and the feature explicitly trades graph-query/write memory away for it, which is the opposite
of what requirements/50's real OOM incident needed (that incident was a graph-memory, not a
vector-memory, shortage). Reusing the existing Postgres/pgvector store (above) also keeps this
project's single stated architecture principle intact — "PostgreSQL stays canonical, Neo4j is a
derived, rebuildable projection" (see [mathbank-graph's skill](</Volumes/External/Developer/knowledge-bank-ingestion/.github/skills/mathbank-graph/SKILL.md>))
— introducing a second, Neo4j-native embedding store would mean keeping two embedding stores in
sync for no current benefit. The HNSW index added in migration 041 lives in **Postgres**, not
Neo4j, consistent with this decision — it accelerates the one-time similarity-pair computation,
not a live per-query path. Revisit Neo4j-native vectors only if a feature genuinely needs ANN
vector search and graph traversal **combined in a single Cypher query**; even then, prefer two
separate queries first (Postgres pgvector finds candidate IDs → a plain Neo4j traversal query
takes that ID list) before adding a second vector store.

### ENR-4 — Project misconception/theory/item taxonomy links directly from stored JSON — ✅ IMPLEMENTED, live-verified

- Supersedes doc 50's `RouteStep`-join derivation (`mathbank-graph/etl/project_misconception_relations.py`): read `route_asset.content->'taxonomy_node_ids'` directly for `MISCONCEPTION`/`THEORY`/`LEARNING_ITEM`(diagnostic) kinds instead of re-deriving the same answer through a graph traversal.
- Backfill the 0.8% (651 of 80,242) `MISCONCEPTION` rows currently missing `taxonomy_node_ids`, by resolving them against their own step's already-recorded `solution_step_requirement` rows (the same source the original enrichment call should have used).

**✅ IMPLEMENTED, live-verified, and with a materially larger scope than originally proposed** — this fix was forced by a real production incident (doc 50 BUG-5 / [GOTCHAS.md §24](/Volumes/External/Developer/knowledge-bank-ingestion/documentation/GOTCHAS.md)): the original `RouteStep`-join companion script's edges got silently destroyed by `route_projection.py`'s own rebuild (a node-level `DETACH DELETE` strips every relationship touching a managed node, regardless of that relationship's own `projection_kind` — confirmed live, the companion script's "distinct tag" protection never actually worked). The fix is exactly the one originally proposed here — project directly from stored JSON, inside `route_projection.py` itself — plus one additional discovery made while doing it:

- **`MISCONCEPTION`'s own `RELATES_TO`** is now projected inside `metadata()`/`_project()` directly from `knowledge.misconception_taxonomy_link` (the canonical junction table from ENR-1, not the raw per-asset `taxonomy_node_ids` — using the already-deduplicated catalog is strictly better than re-deriving from each individual instance). Live: `misconception-concepts` 40,320 edges (fan-in 18.39), `misconception-skills` 27,156 (fan-in 8.16), `misconception-techniques` 11,305 (fan-in 9.21) — 78,781 total, immune to BUG-5's recurrence by construction (recreated by the very rebuild that could otherwise destroy it).
- **New discovery, not in the original proposal:** `THEORY`/`LEARNING_ITEM` assets' own `taxonomy_node_ids` were *already* being read in the existing per-asset loop, but the code only ever wired up an edge when the target was `TECHNIQUE`-typed (`if target["node_type"] == "TECHNIQUE" and asset["kind"] in {"THEORY","LEARNING_ITEM"}`) — confirmed live that this silently dropped **88%** of their taxonomy references (CONCEPT 32,153 + SKILL 27,983 + SUBCONCEPT 9,890 refs vs. TECHNIQUE's 11,993, per-kind, identical distribution across all three asset kinds since they're generated together per checkpoint). Broadened the condition to project every target type, adding four new `graphConfig.js` tabs since Technique already had a visible tab and Concept/Skill did not: `theory-concepts` (42,043 edges, fan-in 19.18), `theory-skills` (27,983, fan-in 8.41), `item-concepts` (42,043, fan-in 19.18), `item-skills` (27,983, fan-in 8.41) — all real, dense, previously-nonexistent structure. Screenshots: [after/theory-concepts.png](/Volumes/External/Developer/knowledge-bank-ingestion/documentation/requirements/assets/51_misconception_canonicalization/after/theory-concepts.png).
- The retired companion script (`mathbank-graph/etl/project_misconception_relations.py`) now carries a `DEPRECATED` docstring explaining exactly why it must not be run again, rather than being silently deleted (kept for historical reference per this project's established convention).
- **Correctness fix required during implementation:** since many different `route_asset` instances now resolve to the same canonical `Misconception` node id, the original per-asset node-append logic would have appended duplicate node dicts with identical ids — harmless for Neo4j's `MERGE` but it would have broken `_project()`'s own node-count reconciliation check (`count != len(data["nodes"])`), which would have made every future projection run raise `ValueError("Tutoring graph metadata counts do not reconcile.")`. Caught in a pre-write dry run (not live) and fixed by gating the node-append (and the `RELATES_TO` projection) behind a "first-seen canonical id" guard, verified via `Counter` over the dry-run output before ever touching Neo4j — zero duplicate `(label, id)` pairs confirmed.
- **Full regression suite re-run after this change**: 720 passed, 113 skipped, 7 failed — same 7 pre-existing/unrelated failures as before this change (confirmed unrelated: an AST-structure test and route-provenance tests affected by independent live-data drift, none touching `route_projection`/`misconception`/`problem_skill`).

### ENR-7 — Rich, human-readable node properties (not just generic `asset_key`s) — ✅ IMPLEMENTED, live-verified (see [doc 50 §10](/Volumes/External/Developer/knowledge-bank-ingestion/documentation/requirements/50_NEO4J_KNOWLEDGE_GRAPH_QUALITY_BUGS.md))

- **Newly confirmed root cause:** the Neo4j nodes for `TheoryItem`/`Misconception`/`Claim` carry **only** `canonical_id` (a UUID), `asset_key` (a generic positional label like `THEORY_STEP_1`/`MIS_STEP_4`), `purpose`, `route_release_id`, `review_status` — **never** the actual `title`/`description` text that already exists in `pedagogy.route_asset.content` and is what a human (or an LLM) would actually want to read. Confirmed live via `MATCH (n:TheoryItem) RETURN properties(n) LIMIT 1` — no `title`/`description` key present at all.
- **Exact root cause location:** [route_projection.py](/Volumes/External/Developer/knowledge-bank-ingestion/mathbank-rest/src/mathbank_rest/route_projection.py)'s `metadata()` function builds each node's `properties` dict (around the `for asset in assets.values(): nodes.append(...)` loop) from only `{canonical_id, route_release_id, asset_key, purpose, review_status}` — `asset` at that point *is* the full `content` JSONB (confirmed: `assets = {row["content"]["key"]: row["content"] for row in asset_rows}`), so `asset["title"]`/`asset["description"]` (and, for `MISCONCEPTION` specifically, `asset["symptom"]`/`asset["why_wrong"]`/`asset["correct_model"]`) are sitting right there, unused, at the point the properties dict is built. `_project()` then writes exactly that properties dict onto the Neo4j node via `SET n += row.properties` — nothing is lost *after* this point, the gap is entirely in what gets put into the dict in the first place.
- **Compounding display bug:** [lib/graphConfig.js](/Volumes/External/Developer/knowledge-bank-ingestion/mathbank-web/lib/graphConfig.js)'s `labelOf()` falls back to `props.asset_key || props.external_id || label` for these four node types — even once `title` exists on the node, `labelOf()` must be updated to prefer it, or the fix is invisible in the UI.
- **Generation-time opportunity (not just a migration backfill):** today, [route_enrichment.py](/Volumes/External/Developer/knowledge-bank-ingestion/mathbank-rest/src/mathbank_rest/route_enrichment.py)'s `enrich()` calls the LLM once per route checkpoint with **no awareness of previously-generated misconceptions/theory/claims at all** — this is *why* near-duplicates accumulate in the first place (§1, the Pythagorean-theorem-misapplication pair). Once ENR-2's embeddings exist, the generation prompt itself should retrieve the nearest existing canonical entries and ask the model to **reuse one if it already fits, or explicitly generate a new one only if it doesn't** — turning deduplication from a post-hoc cleanup into a generation-time habit. This is the "richer OpenAI usage" half of this requirement, distinct from (but complementary to) the richer-Postgres-properties half above.
- **Migration guidance for whoever implements this:** see the dedicated runbook at [reference/GRAPH_NODE_ENRICHMENT_MIGRATION.md](/Volumes/External/Developer/knowledge-bank-ingestion/documentation/requirements/reference/GRAPH_NODE_ENRICHMENT_MIGRATION.md) — exact before/after property schema, exact file/line targets, and validation queries, so this does not need to be re-derived from scratch.
