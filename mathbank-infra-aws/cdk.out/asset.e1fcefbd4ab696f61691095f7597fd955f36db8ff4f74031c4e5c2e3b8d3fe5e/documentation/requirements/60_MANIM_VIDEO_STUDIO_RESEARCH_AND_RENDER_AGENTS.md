# 60. Manim Video Studio: a research agent and a video-render agent over the SceneSpec contract

> **Status: implemented and live-tested.** Both agents are real and run against live infrastructure
> (the Neon Postgres instance, a real `manim` render, and `mathbank-mcp-competitions` for corpus
> grounding) — see §6 for evidence. This is a new, standalone project,
> [mathbank-manim-studio/](/Volumes/External/Developer/knowledge-bank-ingestion/mathbank-manim-studio),
> scoped as a genuinely bounded v1 slice of doc 41's still-open ITL-4 (SceneSpec) / ITL-5 (dual
> Web+Manim renderers), explicitly **not** the full 18-object/23-action vocabulary — see §2 for exact
> scope. **The catalog-promotion workflow this document originally deferred (§2) is now also
> implemented** — DDL (migration 045), REST (mathbank-rest), an admin UI
> (`mathbank-web/admin/manim-studio`), and an agentic integration (4 new MCP tools in
> `mathbank-mcp-competitions`) — see §7 for full detail and evidence. **§8 closes the final gap**:
> a promoted, APPROVED scene is now wireable into a real `visual.interaction_instance` (a new
> `VIDEO_EXPLAINER_V1` template) and attachable, through the existing course-authoring machinery, to
> a published micro-course state — live-verified end to end, including a real student-facing
> `<video>` actually playing inside a published course in a real browser.

## 0. What was asked and why this is a new document, not an ITL-* amendment

The user asked for a "Manim renderer as a service" built as **two long-running agents**:

1. A **research agent** — cloud-ready, long-running — that takes a topic + context and produces a
   detailed JSON output (a `SceneSpec`, per doc 41 ITL-4) with an explanation/narration.
2. A **video creator agent** — given a SceneSpec JSON (generated by (1), or uploaded directly
   against the same schema), actually renders it with Manim, pulling any supplementary corpus data
   it needs via REST or MCP calls.

Both are explicitly **ephemeral**: "persistence in postgres with TTL of 1 day as these need not
have persistence beyond 1 day." This is a genuinely new document (not folded into doc 41) because
doc 41's ITL-1–ITL-14 describe the **canonical, versioned, admin-approved** template/instance/
scene catalog (`visual.scene_spec`, `DRAFT→APPROVED`, bound into published courses) — permanent,
reviewed content. This document's two agents produce **draft, disposable, single-session**
artifacts: a student or admin can ask for an exploratory video on a topic, get one back, and it
evaporates after a day whether or not anyone ever promotes it into the real catalog. Promoting a
generated SceneSpec into `visual.scene_spec` is a deliberate **non-goal** here (§2) — a separate,
future, explicitly-admin-reviewed workflow, consistent with doc 41 ITL-1's "published versions are
never edited in place" and the repository's consistent pattern of LLM output never becoming
canonical without an explicit human approval step.

## 1. Architecture

```text
                    ┌─────────────────────────────┐
  POST /v1/research-jobs  →   scene_research_agent.py  →  OpenAI (tool-calling)
  {topic, context}    │                 │                       │
                       │                 ▼                       ▼
                       │     mathbank-mcp-competitions    corpus grounding
                       │     (MCP stdio client, reused      (real problem/concept/
                       │      from doc 49's server)          technique data)
                       │                 │
                       │                 ▼
                       │     validated SceneSpec JSON + explanation text
                       └─────────────────┼─────────────────────────┐
                                         ▼                         │
                           studio.scene_research_job (Postgres)    │
                           status: PENDING→RUNNING→DONE/FAILED     │
                           expires_at = created_at + 1 day         │
                                         │                         │
  POST /v1/render-jobs  ──────────────────┘                         │
  {research_job_id} or {scene_spec_json}                            │
                       │                                            │
                       ▼                                            │
             scene_video_render_agent.py                            │
                       │                                            │
                       ▼                                            │
         manim_compiler.py: SceneSpec → real Manim Scene source      │
                       │                                            │
                       ▼                                            │
             real `manim` render subprocess → .mp4                  │
                       │                                            │
                       ▼                                            │
         object_store.put_bytes() → video_object_key                │
                       │                                            │
                       ▼                                            │
         studio.video_render_job (Postgres), expires_at +1 day ◄────┘
```

Both job tables live in a new `studio` schema in the **same shared Postgres instance** the rest of
MathBank uses (migration `mathbank-db/sql/044_manim_studio_jobs.sql`) — not a separate database —
because the ephemerality is expressed through `expires_at` + a cleanup script, not through
database-level isolation; this matches the existing `expires_at timestamptz` convention already
used in `visual.asset`/`visual.generation_run` (migration 020).

The service itself (`mathbank-manim-studio/`) is its own standalone FastAPI project (own
`pyproject.toml`, own `.venv`) — not folded into `mathbank-rest` — because it has a materially
different runtime shape (long-running jobs, a `manim`/LaTeX/ffmpeg dependency chain `mathbank-rest`
has no reason to carry) and a different deployability story (this is the kind of workload that
benefits from running in its own container/process, scaled independently of the main API). It
reuses `mathbank-rest`'s corpus data by calling **`mathbank-mcp-competitions`** (doc 49) as an MCP
client over stdio — not by re-implementing REST calls — which is also the first real "another
agent used the MCP server" consumer beyond the demo script doc 49 shipped with.

## 2. Scope: what v1 covers and what it deliberately does not

| In scope (v1, real, tested) | Not in scope (explicit) |
|---|---|
| A 7-object / 7-action SceneSpec vocabulary (§3) sufficient for state-diagram, function-graph and equation-morph explainer videos — a genuine, documented *subset* of ITL-4's full 18-object/23-action surface | The full ITL-4 vocabulary (e.g. `MATRIX_MULTIPLY_STEP`, `POLYNOMIAL` root-animation, `VECTOR` fields) — extending the compiler's object/action handlers is additive future work, not a redesign |
| Two Postgres-backed async job queues (research, render), `PENDING→RUNNING→DONE/FAILED`, polled by an in-process asyncio worker | A distributed task queue (Celery/Redis/SQS) — the Postgres `UPDATE ... WHERE status='PENDING' RETURNING` atomic-claim pattern is sufficient for this workload and keeps the dependency footprint small; swapping the worker loop for a real queue later does not change the job-table contract |
| Real corpus grounding via `mathbank-mcp-competitions` (an MCP stdio client spawned by the research agent) | Admin-authoring UI for these jobs — this is an API/CLI-first deliverable; a UI can be layered on later following modern-ui-design |
| 1-day TTL on both job tables + a cleanup script that also deletes the corresponding object-store video | ~~Promotion of a generated SceneSpec into the canonical catalog~~ — **now implemented, see §7** |
| Real `manim` rendering (verified installed with system ffmpeg/cairo/pango/LaTeX already present) producing a playable `.mp4` | Actual cloud deployment/autoscaling — the service is built *stateless and queue-driven* so it is cloud-ready, but no AWS/GCP resources are provisioned by this document |

## 3. SceneSpec v1 object/action vocabulary (real, implemented, documented)

Reuses doc 41 ITL-4's envelope exactly (`scene_key`, `scene_version`, `objects[]`, `timeline[]`,
validated against the same
[scene_spec.schema.json](/Volumes/External/Developer/knowledge-bank-ingestion/documentation/copilot-instructions/interaction-template-library/schemas/scene_spec.schema.json)
doc 41 already references) plus the same semantic checks doc 41's own
`interaction_validators.validate_scene_spec` applies (no duplicate object ids; every timeline
`targets`/`from`/`to` must reference a declared object id) — ported to a pure, DB-free function
(`mathbank_manim_studio.scene_spec_validation.validate_scene_spec_dict`) since these are
pre-persistence drafts, not rows in `visual.scene_spec` yet.

| Object type | Renders as |
|---|---|
| `TITLE_TEXT` | A `Text(...).to_edge(UP)` heading |
| `TEXT` | A `Text(...)` mobject at a given position |
| `EQUATION` | A `MathTex(...)` mobject (the object's `latex` field) |
| `STATE_NODE` | A labeled `RoundedRectangle`/`Circle` + `Text`, positioned by `x`/`y` |
| `FUNCTION_GRAPH` | `Axes` + `axes.plot(...)` for the object's `expr` (a restricted, safely-`eval`'d single-variable expression) |
| `GRAPH_POINT` | A `Dot` placed on a named `FUNCTION_GRAPH` object at a given `x` |
| `MATRIX` | A `MathTex` rendering of the object's `rows` as a bmatrix |

| Action | Behavior |
|---|---|
| `SHOW` | Fade/Create the target object(s) in |
| `HIDE` | `FadeOut` the target object(s) |
| `WRITE` | `Write(...)` animation (for `TEXT`/`EQUATION`/`TITLE_TEXT`) |
| `HIGHLIGHT` | Flash/indicate the target object(s) (non-color-only: adds a surrounding highlight rectangle *and* a brief scale pulse, consistent with doc 41 ITL-2's "color must never be the only feedback signal") |
| `DRAW_TRANSITION` | Grows an `Arrow` between a `from` and `to` object, with an optional `label` |
| `EQUATION_MORPH` | `Transform` between a `from` and `to` `EQUATION` object |
| `WAIT` | `self.wait(...)` using the gap to the next `at_ms` (or a `duration_ms` field) |

## 4. Postgres schema (migration 044)

```sql
CREATE SCHEMA IF NOT EXISTS studio;

CREATE TABLE studio.scene_research_job (
    scene_research_job_id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    status             text NOT NULL DEFAULT 'PENDING'
                       CHECK (status IN ('PENDING','RUNNING','DONE','FAILED')),
    topic              text NOT NULL,
    context_json       jsonb NOT NULL DEFAULT '{}'::jsonb,
    result_scene_spec  jsonb,
    result_explanation text,
    error_message      text,
    created_at         timestamptz NOT NULL DEFAULT now(),
    updated_at         timestamptz NOT NULL DEFAULT now(),
    expires_at         timestamptz NOT NULL DEFAULT (now() + interval '1 day')
);

CREATE TABLE studio.video_render_job (
    video_render_job_id    uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    status                 text NOT NULL DEFAULT 'PENDING'
                           CHECK (status IN ('PENDING','RUNNING','DONE','FAILED')),
    source_research_job_id uuid REFERENCES studio.scene_research_job(scene_research_job_id)
                           ON DELETE SET NULL,
    scene_spec_json        jsonb NOT NULL,
    video_object_key       text,
    video_duration_ms      integer,
    error_message          text,
    created_at             timestamptz NOT NULL DEFAULT now(),
    updated_at             timestamptz NOT NULL DEFAULT now(),
    expires_at              timestamptz NOT NULL DEFAULT (now() + interval '1 day')
);

CREATE INDEX idx_scene_research_job_expires ON studio.scene_research_job (expires_at);
CREATE INDEX idx_video_render_job_expires ON studio.video_render_job (expires_at);
```

A standalone cleanup script (`scripts/cleanup_expired_jobs.py`) deletes the object-store video for
every expired `video_render_job` row, then deletes expired rows from both tables — run via
`make cleanup` or an external cron; it is intentionally not wired into a cloud scheduler here (no
cloud resources are provisioned by this document, per §2).

## 5. API

| Endpoint | Purpose |
|---|---|
| `POST /v1/research-jobs` `{topic, context?}` | Enqueue a research job; returns `{id, status: PENDING}` |
| `GET /v1/research-jobs/{id}` | Poll status; once `DONE`, includes `result_scene_spec` + `result_explanation` |
| `POST /v1/render-jobs` `{research_job_id}` or `{scene_spec_json}` | Enqueue a render job from either source |
| `GET /v1/render-jobs/{id}` | Poll status; once `DONE`, includes `video_object_key` and `video_duration_ms` |
| `GET /v1/render-jobs/{id}/video` | Streams the rendered `.mp4` |

An in-process asyncio worker (started on FastAPI `startup`) polls both tables every 2 seconds,
atomically claims one `PENDING` row (`UPDATE ... SET status='RUNNING' WHERE id=:id AND
status='PENDING' RETURNING ...`), and executes the corresponding agent.

## 7. Catalog-promotion workflow: DDL, REST, admin UI, agentic integration

The one deliberate non-goal §2 originally flagged — promoting a generated SceneSpec into the
canonical `visual.scene_spec` catalog (doc 41 ITL-1/ITL-4) — is now implemented, as a genuine
cross-service admin review-and-approve workflow. `mathbank-manim-studio`'s job queue stays purely
ephemeral/disposable (§4); this workflow is the one deliberate, explicit bridge from a disposable
draft into permanent, versioned, admin-reviewed catalog content.

**Design principle carried over from doc 49:** `mathbank-manim-studio` and `mathbank-rest` remain
genuine peer services — `mathbank-rest`'s new `scene_spec_promotion.py` calls
`mathbank-manim-studio`'s REST API (list candidates, fetch the rendered video, mark-promoted)
rather than reading `studio.*` tables directly, even though both share one physical Postgres
instance. The only exception is `studio.video_render_job.promoted_scene_spec_id`, a real
cross-schema foreign key into `visual.scene_spec` (migration 045) — safe because it is the same
physical database, and it is only ever written by `mathbank-manim-studio`'s own
`mark-promoted` endpoint, never by `mathbank-rest` reaching into the table directly.

### DDL (migration 045)

- `visual.scene_spec` gains `rendered_video_asset_id uuid REFERENCES visual.asset` and
  `source_studio_job_id text` (a lineage pointer, deliberately *not* a real FK — the ephemeral job
  row it points to is expected to expire and be deleted, while an APPROVED `scene_spec` is
  permanent; a dangling lineage pointer after TTL expiry is expected and harmless).
- `studio.video_render_job` gains `promoted_scene_spec_id uuid REFERENCES visual.scene_spec`, so
  the Manim Video Studio's own candidate list can exclude already-promoted jobs without needing to
  ask `mathbank-rest`.

### REST (mathbank-rest, `routers/interaction_templates.py`, all `X-Admin-Api-Key`-gated)

| Endpoint | Purpose |
|---|---|
| `GET .../scenes/promotable-candidates` | Proxies `mathbank-manim-studio`'s `GET /v1/render-jobs?status=DONE&unpromoted_only=true`, filtered again locally against `visual.scene_spec.source_studio_job_id` (a stronger idempotency guard than trusting the peer service's own flag alone) |
| `POST .../scenes/promote` | `scene_spec_promotion.promote_render_job` — fetches the render job + its video from `mathbank-manim-studio`, inserts a new DRAFT `visual.scene_spec` + `visual.asset` row, tells the peer service the job is now promoted (best-effort) |
| `GET .../scenes`, `GET .../scenes/{id}`, `GET .../scenes/{id}/video` | List/detail/video-bytes for the catalog |
| `POST .../scenes/{id}/validate`, `POST .../scenes/{id}/approve` | Reuses the *existing* `interaction_validators.validate_scene_spec` (no new validation logic) and the same DRAFT→APPROVED pattern already used for `interaction_instance`/`feedback_template` |

`mathbank-manim-studio` itself gained a matching `GET /v1/render-jobs` (list/filter) and
`POST /v1/render-jobs/{id}/mark-promoted` (the one write endpoint sensitive enough to need its own
admin-key check, reusing the exact `X-Admin-Api-Key` header convention via a shared secret value).

### Admin UI (`mathbank-web/app/admin/(protected)/manim-studio`, modern-ui-design)

A new sidebar entry ("Manim video studio") renders a two-column page: pending-promotion candidates
on the left (scene key, object/timeline counts, a canonical-code input + Promote button), catalog
scenes on the right (a clickable list; selecting one opens a detail panel with the real `<video>`
player and Validate/Approve buttons for DRAFT rows). `PageHeader`/`Pill`/`EmptyState` throughout, no
hard-coded colors, consistent with every other admin page's shell/breadcrumb conventions.

### Agentic integration (4 new tools in `mathbank-mcp-competitions`)

`list_promotable_scenes`, `promote_scene_to_catalog`, `validate_scene_in_catalog`,
`approve_scene_in_catalog` — each takes an explicit `admin_api_key` argument and is a thin proxy to
the REST endpoints above; the key is validated by `mathbank-rest`, never by the MCP server itself
(FastMCP's "visibility is not security" principle, already established in doc 49 §1). This is the
first time doc 49's admin-key-hardening caveat (FMI-7) actually applies to that server — previously
moot because nothing admin-scoped was exposed.

### Evidence (live, both through direct REST and through the real MCP tool layer)

- A full live round trip — research job → render job → list candidates → promote → validate →
  approve — was run three separate times: once via raw `httpx` calls (manual verification), once as
  a `pytest` integration test in `mathbank-rest/tests/test_scene_spec_promotion.py` (opt-in,
  `MANIM_STUDIO_LIVE_TEST=1`), and once through the real MCP protocol path in
  `mathbank-mcp-competitions/tests/test_scene_promotion_tools.py` (same opt-in gate). All three
  passed, producing a real, playable, APPROVED catalog video (confirmed by extracting and visually
  inspecting a frame with `ffprobe`/`ffmpeg`, showing the correct Jensen's-inequality/Cauchy-Schwarz
  content).
- The admin UI was driven live in a real browser as "Admin": promoted a real candidate (the counts
  moved from "1 pending review / 0 in catalog" to "0 pending review / 1 in catalog"), opened the new
  DRAFT scene's detail panel (a real HTML5 `<video>` element playing the actual rendered clip), and
  confirmed the status pill updated to "APPROVED" after approval.
- Idempotency was verified: re-promoting an already-promoted render job returns `409` with a clear
  message, both via REST and via the MCP tool (same underlying `PromotionError`).
- All test data created during this verification pass was deleted from the live database afterward
  (using the existing `visual.allow_purge` escape hatch for the one APPROVED row, consistent with
  how that guard trigger is designed to be bypassed for exactly this kind of administrative purge).

## 8. Wiring promoted scenes into `interaction_instance` and published micro-courses

§7 stops at an APPROVED `visual.scene_spec` catalog row — a permanent, versioned, admin-reviewed
scene, but not yet anything a student can encounter inside a course. This section closes that gap:
an APPROVED scene can become a real `visual.interaction_instance`, attachable to a published
micro-course state through the *existing* course-authoring machinery (requirements/40/43) with
zero new course-binding code.

**Design choice: a new, minimal "watch this video" interaction template, not forcing the scene into
one of the 5 existing interactive templates.** The only `PUBLISHED` templates before this feature
(`STATE_GRAPH_EXPLORER_V1`, `TRANSITION_MATRIX_EDITOR_V1`, `RECURRENCE_EXPLORER_V1`,
`POLYNOMIAL_ROOT_COEFFICIENT_EXPLORER_V1`, `FUNCTION_GRAPH_EXPLORER_V1`) are genuinely interactive —
their `instance_config` drives a clickable/draggable widget rendered by hand-written React, with
`success_criteria` like `{"type": "EXPLORATION", "description": "Visit both states..."}`. A
Manim-rendered explainer video is passive — there is nothing to manipulate, only something to
watch — so it gets its own template, `VIDEO_EXPLAINER_V1`, idempotently self-seeded the first time
an admin creates an instance from a scene. Its control/icon vocabulary (`VIDEO_TIMELINE` control;
`VIDEO`/`PLAY`/`PAUSE`/`COMPLETE` icons) already existed in the seed catalog, unused by any template
until now — strong evidence this exact use case was anticipated by the original ITL-2 catalog design.

### What was added

| Layer | Change |
|---|---|
| Service (`mathbank-rest/scene_spec_promotion.py`) | `_ensure_video_explainer_template` (idempotent template+version seed), `create_video_explainer_instance` (APPROVED scene → new `PENDING_REVIEW` interaction_instance), `approve_scene_and_validate_asset` (scene approval also flips the linked `visual.asset.validation_status` to `VALID` — see "why" below) |
| REST (`mathbank-rest`) | `POST /v1/admin/interaction-templates/scenes/{id}/create-instance`; the *existing* `/instances/{id}/approve`, `/micro-courses/.../interactions` (list) and `/micro-courses/states/{id}/interactions` (attach) endpoints are reused unchanged |
| REST (`mathbank-rest`, read-path fix) | `micro_course_service.get_published_asset` gained a second resolution path — an asset reachable via an attached interaction's `scene_spec_id → rendered_video_asset_id`, not only the direct `micro_course_state_asset` attachment — since a Manim video is never directly attached to a state, only indirectly through its interaction |
| Student payload | Both interaction-listing queries (student course reader + admin preview) now also select `scene.rendered_video_asset_id` |
| Frontend (`mathbank-web`) | A new `VideoExplainer` component in `InteractionTemplateRenderer.jsx` — a plain `<video>` tied to the existing `/api/rest/micro-courses/{code}/assets/{asset_id}/content` proxy, recording a `VIDEO_WATCHED` interaction event via the *existing* telemetry callback on `ended` |

**Why approving a scene also validates its asset:** `get_published_asset` (the student-facing
stream endpoint) requires `visual.asset.validation_status = 'VALID'`; a freshly-promoted video
starts `'PENDING'`. Since the admin literally watches the video in the catalog review panel (§7)
before clicking Approve, that click *is* the human judgment the `VALID` flag is supposed to
represent — so `approve_scene` now performs both state transitions atomically, rather than
requiring a second, separate "validate this asset" admin action nobody would know to take.

### Evidence (live, full stack, real student-facing playback)

A full, live, single pass proved every layer: promote a real render job → approve the scene
(asset flips to `VALID`) → `create-instance` (new `PENDING_REVIEW` `VIDEO_EXPLAINER_V1` instance) →
approve the instance (existing endpoint) → create a throwaway course + release + module + state
(existing endpoints) → attach the interaction (existing endpoint, unmodified) → validate + review +
publish the release (existing endpoints) → `GET` the published course as a student → confirmed
`template_key: "VIDEO_EXPLAINER_V1"` and a real `rendered_video_asset_id` in the payload → downloaded
142,840 bytes of valid MP4 through the *student* asset-streaming endpoint (not the admin one) →
extracted and visually confirmed a correct frame (`AM-GM Inequality for Two Positive Numbers`) → then
opened the same published course in a real, already-authenticated browser session and confirmed the
video actually renders and plays (0:00/0:08, correct native controls) inside the live
single-active-item course reader.

Two real bugs were found and fixed during this pass (documented in `GOTCHAS.md` §37-38, not
repeated here): a cross-service transaction-visibility race where the "mark promoted" callback to
`mathbank-manim-studio` fired before mathbank-rest's own insert had committed (fixed by giving
`promote_render_job` its own transaction boundary, committed before the cross-service call); and an
invented `object://` URI scheme that silently diverged from the codebase's real `object-store:`
convention, only surfacing once the student-facing asset path (which checks that exact prefix) was
exercised for the first time.

**Known limitation, accepted as a one-time cost of this verification pass, not a design flaw:** a
published micro-course's `pedagogy.micro_course_review` row is deliberately append-only (guarded by
`pedagogy.forbid_update()`), so a throwaway test course used to prove this pipeline cannot be fully
deleted once published — only its state/interaction *content* can be cleaned up, leaving an empty,
clearly-named (`MC-WIRING-TEST`) shell course and its permanent review audit trail. This is the same
"nothing published is ever silently erased" principle already enforced everywhere else in the
schema, not a gap introduced by this feature.

## Cross-document relationship

Builds on doc 41's SceneSpec contract (ITL-4) and reuses doc 49's `mathbank-mcp-competitions` as
its corpus-grounding client — the first real second consumer of that MCP server. §7's promotion
workflow is the one deliberate write path into doc 41's canonical `visual.scene_spec` catalog;
everything else in `studio.*` remains ephemeral and untouched by doc 41's own schema/code. §8
additionally reuses doc 40/43's existing course-authoring/attachment endpoints unmodified and doc
41's own `VIDEO`/`PLAY`/`PAUSE`/`COMPLETE`/`VIDEO_TIMELINE` catalog vocabulary, previously unused by
any template.
