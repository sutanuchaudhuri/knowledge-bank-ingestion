03 · Graph

Knowledge Graph (Neo4j AuraDB)

Postgres is the system of record; this graph is a derived, re-buildable projection that connects problems, solution steps, learning items and the skill/concept taxonomy. It powers the graph leg of hybrid search, the tutor's learning context, prerequisite and practice lookups, and admin coverage checks. Below: the current model, what each relationship means pedagogically, a Power-of-a-Point worked example and a catalogue of real queries. The canvas further down is a historical AuraDB export (AMC10 2023), kept for reference.

GThe graph at a glance

Neo4j is rebuilt from Postgres by three projectors. It contains no student data, no step text, no question text and no answers. Every node is MERGEd on canonical_id, which is the Postgres primary key (a UUID for corpus rows, a book-scoped key for textbook rows), so re-running a projection is idempotent. The authoritative label/edge/property inventory is GRAPH_SCHEMA.md.

G1 · Corpus and skill layer

Problems are linked to what they test (Concepts), how they are solved (Techniques) and what a learner must be able to do (Skills). Skill edges carry pedagogy: role, required_level (1–5), importance, confidence, source and review_status.

flowchart LR
    Competition -->|HAS_PAPER| Paper
    Paper -->|HAS_PROBLEM| Problem
    Problem -->|HAS_SOLUTION| Solution
    Problem -->|"TESTS {role}"| Concept
    Problem -->|"USES_TECHNIQUE {role}"| Technique
    Problem -->|"REQUIRES / PRACTICES / TESTS {role, required_level, importance}"| Skill
    Skill -->|PART_OF| Concept
    Skill -->|"PREREQUISITE_OF / PART_OF / BUILDS_ON"| Skill2["Skill"]
    Concept -->|"PART_OF / PREREQUISITE_OF / BUILDS_ON"| Concept2["Concept"]
    Concept -->|"CONCEPT_RELATION {relation_type}"| Concept2

G2 · Solution-step layer (textbooks)

Each worked solution is broken into ordered parts and steps. Steps are linked to each other by a dependency DAG and to the taxonomy by USES_* edges. That lets the tutor ask "which earlier step does this one rely on, and what skill does it use?"

flowchart LR
    Solution -->|"HAS_PART {part_ordinal}"| SolutionPart
    SolutionPart -->|"HAS_STEP {step_index_in_part}"| StepA["SolutionStep"]
    StepA -->|"NEXT"| StepB["SolutionStep"]
    StepB -->|"DEPENDS_ON / USES_RESULT_FROM / DERIVES_FROM"| StepA
    StepB -.->|"ALTERNATIVE_TO / JOINS_AT"| StepC["SolutionStep"]
    StepA -->|USES_SKILL| Skill
    StepA -->|USES_CONCEPT| Concept
    StepA -->|USES_SUBCONCEPT| Subconcept["Concept:Subconcept"]
    StepA -->|"USES_TECHNIQUE {confidence, review_status}"| Technique

DAG edges carry logical_dependency, confidence, source_type, review_status and approval_method. Rejected dependencies are excluded at projection. Step techniques (migration 017, rules-v1) are projected only when APPROVED: 4,354 tags on 3,397 of 7,814 steps. The dotted types are supported by the projector, but the Prasolov package uses only NEXT and DEPENDS_ON.

G3 · Learning-item layer

A learning item is a smaller, answer-checkable rehearsal of part of a problem: a method-recognition MCQ, a "first move" subproblem, a "next intermediate" step. Only APPROVED, student-visible, no-proof items are projected.

flowchart LR
    LearningItem -->|DERIVED_FROM| Problem
    LearningItem -->|"ANCHORED_AT {ordinal}"| SolutionStep
    LearningItem -->|ASSESSES| Skill
    LearningItem -->|TARGETS_CONCEPT| Concept
    LearningItem -->|TARGETS_SUBCONCEPT| Subconcept["Concept:Subconcept"]

G4 · Taxonomy hierarchy

The Prasolov taxonomy (1 domain, 30 chapter concepts, 214 section subconcepts, 202 skills, 54 techniques) is bridged into knowledge.concept, knowledge.skill and knowledge.technique at import. Book HAS_SUBCONCEPT is reversed into child PART_OF parent. A Subconcept is a Concept node with a second label, so concept queries still find it.

    S10["Subconcept GEO.C03.S10 · The radical axis"] -->|PART_OF| C03["Concept GEO.C03 · Circle Geometry"]
    C03 -->|PART_OF| GEO["Concept GEO · Geometry (domain)"]

Taxonomy SUPPORTS edges stay in pedagogy.taxonomy_edge; they shape the taxonomy vector text (see Vector models) but are not projected as graph edges.

EWorked example — Power of a Point (Prasolov 3.50)

"Circle S and point P are given on the plane. A line drawn through point P intersects the circle at points A and B. Prove that the product PA · PB does not depend on the choice of the line." This is the Power of a Point theorem, filed in Chapter 3 "Circles", section 10 "The radical axis". The graph below is drawn from the imported package rows (no step text is projected; the step text is shown here only to make the example readable).

How the tutor reads it

A student stuck on step 02 (the similarity) gets a diagnosis ranked first by step 02's own skill (similar triangles), then by the skills of the steps it relies on, then by subconcept and concept.

Recovery

Items anchored at that step (PMAIN-T5) or assessing that skill are the first candidates for a short detour; then the student resumes step 02.

Practice and search

"Power of a point" queries hit 3.50 through vectors and through the graph leg (the radical axis tags), and RRF fuses both ranks. Easier practice looks for problems that REQUIRE the same skill at a lower level.

IDs: textbook keys are book-scoped (PRASOLOV_PGV1/STEP-3.50-MAIN-01, PRASOLOV_PGV1/3.50-V3-PMAIN-T3); taxonomy slugs are the lower-cased node ids (geo.c03.s10, skill.geo.apply_the_radical_axis). The student walk-through is Turn 4 of Tutor Interaction.

1 · Hybrid search — the graph leg live · db/hybrid_search.py graph_candidates 
// tags whose name/slug contains a query term, plus tags of the top semantic hits ("seeds")
CALL {
  MATCH (tag) WHERE (tag:Concept OR tag:Technique OR (tag:Skill AND tag.review_status='REVIEWED'))
  WITH tag, size([term IN $terms WHERE toLower(coalesce(tag.name,'')+' '+
        replace(coalesce(tag.slug,''),'-',' ')) CONTAINS term]) AS matches
  WHERE matches > 0 RETURN tag, matches, [] AS seed_codes
  UNION ALL
  MATCH (seed:Problem)-[sr:TESTS|USES_TECHNIQUE|REQUIRES|PRACTICES]->(tag)
  WHERE seed.canonical_code IN $seeds AND sr.review_status='REVIEWED' ...
  RETURN tag, 0 AS matches, collect(DISTINCT seed.canonical_code) AS seed_codes
}
...
MATCH (p:Problem)-[link:TESTS|USES_TECHNIQUE|REQUIRES|PRACTICES]->(tag)
WHERE link.review_status='REVIEWED'
WITH p, sum(matches*2+shared) AS score, collect({kind:type(link), slug:tag.slug}) AS evidence
RETURN p.canonical_code, score, evidence ORDER BY score DESC LIMIT $limit

Query "radical axis power of a point" → terms radical, axis, power, point → the tag The radical axis matches twice → every problem tagged with it scores. The graph rank is fused with the semantic and lexical ranks by 1/(60+rank) (see Vector models). The tags are resolved first because expanding every reviewed Problem→tag link before filtering took 30 s+ on Aura. If Neo4j is down, search still returns, with a warning.

2 · Learning context for a problem live · pedagogy.py → GET /v1/tutor/learning-context/{code} 
MATCH (p:Problem {canonical_code:$code})
OPTIONAL MATCH (p)-[r:REQUIRES|PRACTICES|TESTS]->(s:Skill)
WHERE r.review_status = 'REVIEWED' AND s.review_status = 'REVIEWED'
RETURN properties(s) AS skill, properties(r) AS edge, type(r) AS relation_type

MATCH (p:Problem {canonical_code:$code})
OPTIONAL MATCH (p)-[r:TESTS|USES_TECHNIQUE]->(n)
WHERE (n:Concept OR n:Technique) AND r.review_status = 'REVIEWED'
RETURN labels(n)[0] AS label, n.slug AS slug, n.name AS name, ...

The agent tool get_problem_learning_context calls this before tutoring. For 3.50 it returns the primary skill Apply the radical axis and the two supporting step skills, once those edges are REVIEWED. The statement comes from Postgres; the solution is never returned.

3 · Prerequisite path for a skill live · pedagogy.py _prerequisites → GET /v1/tutor/prerequisites/{slug} 
UNWIND $slugs AS slug
MATCH path=(prior:Skill)-[:PREREQUISITE_OF*1..{max_depth}]->(target:Skill {slug:slug})
WHERE all(n IN nodes(path) WHERE n.review_status = 'REVIEWED')
  AND all(r IN relationships(path) WHERE r.review_status = 'REVIEWED')
WITH prior, target, path ORDER BY length(path)
WITH prior, target, min(length(path)) AS depth, head(collect(path)) AS evidence_path
...
RETURN properties(prior) AS skill, depth, required_for, evidence
ORDER BY depth DESC, prior.slug LIMIT $limit
// a second query probes depth max_depth+1 so the response can say "deeper prerequisites may exist"

Used by the agent tool get_prerequisite_path. Gotcha: Prasolov skills have no PREREQUISITE_OF edges, so for geometry this returns empty and the step DAG (query 5) serves as the prerequisite source instead. An empty result is "no reviewed evidence", not "no prerequisites".

4 · Easier practice on the same skill live · pedagogy.py easier_practice → GET /v1/tutor/practice/{code} 
MATCH (original:Problem {canonical_code:$code})-[a:REQUIRES|PRACTICES|TESTS]->
      (s:Skill)<-[b:REQUIRES|PRACTICES|TESTS]-(candidate:Problem)
WHERE candidate <> original AND s.review_status = 'REVIEWED'
  AND a.review_status = 'REVIEWED' AND b.review_status = 'REVIEWED'
  AND type(a) = type(b) AND a.role = b.role
  AND a.required_level IS NOT NULL AND b.required_level IS NOT NULL
  AND b.required_level < a.required_level
WITH candidate, collect({skill_slug:s.slug, original_level:a.required_level,
     candidate_level:b.required_level, ...}) AS evidence
MATCH (competition:Competition)-[:HAS_PAPER]->(paper:Paper)-[:HAS_PROBLEM]->(candidate)
RETURN candidate.canonical_code, competition.name, paper.year, evidence

"Same skill, gentler level" — the agent tool find_easier_same_skill_problems. It needs a populated required_level on both edges. The Prasolov import writes importance and role but no level, so for textbook problems this returns empty, and the step-level vector practice (Vector models, example 3) is the fallback.

5 · Walk the step DAG backwards from a stuck step illustrative Cypher · runtime uses the Postgres copy 
MATCH (stuck:SolutionStep {canonical_id: 'PRASOLOV_PGV1/STEP-3.50-MAIN-02'})

OPTIONAL MATCH (earlier)-[:USES_SKILL]->(sk:Skill)

VReview filtering and visibility

  • Projectors write PENDING, REVIEWED and REJECTED edge metadata. Readers filter to REVIEWED (corpus/skill layer) or APPROVED (step techniques).
  • Rejected step dependencies and unapproved learning items are excluded at projection time.
  • The pedagogy layer is replaced atomically inside Neo4j: a failed refresh keeps the previous layer; a successful one propagates downgrades.
  • The step projector prunes stale parts, steps and items by projection_version.
  • No step text, question text, choices or answers are projected. Graph visibility never implies a student may see a solution.

NWhat the graph is not used for

Runtime diagnosis

Reads the Postgres step DAG and taxonomy columns (fast, transactional, one database).

Recovery ranking

SQL taxonomy closeness over learning items; no graph and no vectors.

Student state

Attempts, mastery and events live only in Postgres. The MASTERED/STRUGGLES_WITH learner edges remain planned.

P0Skill-level graph contract

A Skill is an actionable learning objective with an optional ordinal level from 1 to 5. A Concept is its subject area. The new relationship contract supplements, rather than replaces, the legacy Concept and Technique projection shown below.

Relationship directionPedagogical meaning
Skill → PART_OF → ConceptTopic membership; not evidence of prerequisite ordering.
prior Skill → PREREQUISITE_OF → dependent SkillThe prior skill is needed before the dependent skill. Incoming traversal finds prerequisites.
child Skill → PART_OF → parent SkillObjective decomposition. Distinct from prerequisite ordering.
Problem → REQUIRES → SkillA skill needed to engage with the problem.
Problem → PRACTICES → SkillA skill exercised by working through the problem.
Problem → TESTS → SkillAn assessed objective. The target label matters: legacy TESTS → Concept is not a Skill edge.

Problem–Skill associations retain role, required_level (1–5), importance, confidence, source, and review_status. Source and review metadata must survive projection; missing approval is not implicitly REVIEWED. The projection inventories all PENDING, REVIEWED, and REJECTED edge metadata; graph visibility is not tutor eligibility. Tutor retrieval admits reviewed evidence only. Difficulty dimensions retain provenance rather than being inferred from graph position. Generated metadata starts PENDING, even when confidence is high; REJECTED remains distinguishable and is not eligible reviewed evidence.

Reviewed prerequisites

Match the dependent skill, then follow incoming PREREQUISITE_OF relations. Filter the relationship evidence for review approval. Do not substitute HAS_SUBCONCEPT or PART_OF ancestry for a learning dependency.

Easier, same-skill practice

Keep the target skill fixed, require reviewed skills and Problem–Skill associations, then compare required levels on the same skill. No qualifying evidence means “unavailable”, not a made-up prerequisite or practice recommendation.

RETURN prior, r.source AS source, r.confidence AS confidence, r.review_status AS review_status

No learner node is needed for anonymous prerequisite lookup. P2 personalization would add learner-specific evidence later. An empty result does not prove there are no prerequisites: metadata may be absent, PENDING, or not yet projected.

Use case: coverage audit — which competitions are under-classified? operational, used in GOTCHAS #16 
MATCH (comp:Competition)-[:HAS_PAPER]->(:Paper)-[:HAS_PROBLEM]->(pr:Problem)
OPTIONAL MATCH (pr)-[:TESTS]->(:Concept)
WITH comp.name AS competition, count(DISTINCT pr) AS problems,
     count(DISTINCT pr) FILTER (WHERE EXISTS { (pr)-[:TESTS]->(:Concept) }) AS tagged
RETURN competition, problems, tagged, round(100.0 * tagged / problems, 1) AS pct_tagged
ORDER BY pct_tagged

This exact pattern (run against Postgres, not Cypher, for the production check) is what surfaced that SMT/CHMMC/PUMaC/CMM were 0-5% classified vs ~99% for AMC/AIME — directly motivating the parallel classification batches covered in the ingestion page.

DConstraints — what keeps the graph consistent

CREATE CONSTRAINT competition_id IF NOT EXISTS FOR (n:Competition) REQUIRE n.canonical_id IS UNIQUE
CREATE CONSTRAINT paper_id       IF NOT EXISTS FOR (n:Paper)       REQUIRE n.canonical_id IS UNIQUE
CREATE CONSTRAINT problem_id     IF NOT EXISTS FOR (n:Problem)     REQUIRE n.canonical_id IS UNIQUE
CREATE CONSTRAINT concept_id     IF NOT EXISTS FOR (n:Concept)     REQUIRE n.canonical_id IS UNIQUE
CREATE CONSTRAINT technique_id   IF NOT EXISTS FOR (n:Technique)   REQUIRE n.canonical_id IS UNIQUE
CREATE CONSTRAINT solution_id    IF NOT EXISTS FOR (n:Solution)    REQUIRE n.canonical_id IS UNIQUE

Every canonical_id is the Postgres UUID itself — the constraint is what makes MERGE-based corpus projection idempotent. The pedagogical layer uses atomic replacement: a failed refresh protects the previous live layer, while successful refreshes propagate review downgrades instead of retaining stale REVIEWED edges. Projection inventory and tutor approval filters remain separate responsibilities.
