# Learner-side findings (REST on DynamoDB, test-writable mode)

Source: `python -m apitest --mode test-writable --suite journeys` over the `learner_*` journeys (latest full run: 930 checks, 7 failed; every
failure below is a kept check). No server `Traceback` appeared in the server log; every finding is a wrong status, an
accepted-but-invalid request, a leaking field or a degraded response. Nothing under `src/` was changed.

Severity: **High** = data loss / security / wrong result for users, **Medium** = wrong behaviour users can hit, **Low** = hygiene.

## F1 (Medium) — a failed hint generation still spends the help level and returns `hint_text: null`

- Endpoint: `POST /v1/attempts/{id}/steps/{step}/hint` (and `GET .../hints`, which regenerates every uncached level).
- Request: level-2 hint on `PRASOLOV_PGV1/STEP-1.1-A-01` (level 1 was already cached; levels 2–4 are generated by the model and cached per step).
- Observed: `200 {"help_level":2,"help_kind":"CONCEPT_REMINDER","hint_text":null,"state_version":5,"hint_source":"UNAVAILABLE"}`.
  The step's `help_level_used` was already committed (the attempt later counts as `SUCCESS_WITH_HELP`) although the learner got no text; the
  model call was paid for and thrown away. Log: `hint generation failed for PRASOLOV_PGV1/STEP-1.1-A-01 level 2: ReadOnlyViolation`.
- Cause in this run: after generating, `step_tutor.get_or_create_hint` writes the text into the **content** table (`ContentHint`, PK `HINT#<step>`).
  In `test-writable` the content table is `dev` (write-guarded), so the write raised `ReadOnlyViolation`, which is not `StoreFrozen`, and the
  blanket `except Exception` in `_hint_text` turned it into `UNAVAILABLE`. The same happens in production if the runtime role cannot write
  the content table.
- Expected: (a) the help level must not be consumed (or the call must return 503) when no hint text can be delivered; (b) the cache write is
  an optimisation and must be best-effort like `StoreFrozen` (return the generated text anyway); (c) a runtime learner request writing to
  the *content* table deserves a product decision (move the hint cache to a runtime table).
- Suspected source: `src/mathbank_rest/step_tutor.py:246-252` (only `StoreFrozen` is swallowed), `src/mathbank_rest/routers/step_runtime.py:190-199`
  (`_hint_text` swallow-all) and `:202-212` (help level escalated before the text exists), `:219-228` (GET regenerates; each uncached level is a paid
  model call), `src/mathbank_rest/stores/content/pedagogy.py:673-683`.
- Check: `journey:learner_solve_steps / hint 2 escalates to level 2 and delivers text`.

## F2 (Medium) — recovery items accept an empty answer: worked example auto-acknowledged, MCQ graded INCORRECT

- Endpoint: `POST /v1/recovery-plans/{plan}/items/{item}/responses`.
- Request: body `{"state_version": N}` only (no `acknowledged`, no `choice_index`, no `response_text`).
- Observed: THEORY item -> `200 {"result":{"result":"SUCCESS","verdict":"ACKNOWLEDGED"},"decision":"ADVANCE"}` (the learner never acknowledged);
  MCQ item -> `200 {"verdict":"INCORRECT","decision":"RETRY"}` (an empty request burns one of the learner's tries and counts towards
  alternate items / exhaustion).
- Expected: `422/409` — a worked example needs an acknowledgement and an MCQ a valid `choice_index` (the subproblem path already raises
  `response_text is required`). An out-of-range `choice_index` is correctly rejected (4xx).
- Suspected source: `src/mathbank_rest/step_recovery_logic.py:148-149` (THEORY ignores `response["acknowledged"]`) and `:151-153` (`idx` falls back
  to `None` and is graded wrong); `routers/step_runtime.py:311-315` makes all three answer fields optional with no cross-check.
- Checks: `journey:learner_recovery / answer a THEORY item with an empty answer -> 4xx`, `... a LEARNING_ITEM item with an empty answer -> 4xx`.

## F3 (Low–Medium) — a lost password-change race returns a store-internal error body

- Endpoint: `POST /v1/learner/me/password`, three concurrent requests with the same current password.
- Observed: one `200`, others `403` or `409 {"detail":"condition_failed","op":"PROFILE:PROFILE"}` — the raw `ConditionFailed` store error
  (internal operation label) instead of a client message. 409 is acceptable; the body is not.
- Expected: a mapped, human-readable 409 (e.g. "your password was changed by another request"), like the other conflicts in the learner store.
- Suspected source: `src/mathbank_rest/stores/learner/identity.py:444-450` (`uow.update(... expected=..., increment=...)` has no `conflict=`),
  rendered by `src/mathbank_rest/stores/errors.py:119-123` (`StoreError.body()` exposes `op`).
- Check: `journey:learner_concurrency / a lost password-change race returns a client-facing message ...`.

## F4 (Low) — validation errors echo the plaintext password back

- Endpoint: `POST /v1/learner/register` (any body-level validation failure on `/login` and `/me/password` behaves the same).
- Request: `{"email": "...", "password": "Apitest-Passw0rd!1", "first_name": "X"}` (last_name missing).
- Observed: `422 {"detail":[{"type":"missing","loc":["body","last_name"],"input":{"email":"...","password":"Apitest-Passw0rd!1","first_name":"X"}}]}`
  — FastAPI's default handler returns the whole request body in `input`. For a too-short password `input` is the password value itself.
- Expected: no credential material in error bodies (clients, proxies and the gateway log them); strip `input` from validation errors.
- Suspected source: no `RequestValidationError` handler is installed: `src/mathbank_rest/profiles.py:169` (`create_app`) / `main.py`;
  models `src/mathbank_rest/routers/learner.py:31-45`.
- Check: `journey:learner_identity / leak: register missing last_name -> 422`.

## F6 (Low) — route attempt status vocabulary differs between endpoints

- `POST/GET /v1/tutor/route-attempts[/{id}]` returns `"status": "active"` / `"finished"` while `GET /v1/learner/route-attempts`
  returns (and filters by) `"IN_PROGRESS"` / `"FINISHED"` for the same attempt.
- Expected: one vocabulary.
- Suspected source: `src/mathbank_rest/route_runtime.py:404` (`"active" if instruction else "finished"`) vs the list rows in `stores/learner/routes.py`.
- Check: `journey:learner_route_attempts / route status vocabulary is the same in the attempt view and in the learner list`.

## Informational (not failures)

- **Notification producers are unwired.** `GET /v1/notifications/me` is always empty: the requirement-59 triggers (`record_quiz_graded`,
  `record_micro_course_item_graded`, `record_micro_course_activity_graded`, `record_admin_review_needed` in `notifications.py:108-160`) are
  `TODO` and never called. A full micro-course (graded activities) and a completed solve leave the inbox empty. Shapes, paging, `read`,
  `read-all` and the 404/422/401 behaviour are asserted and pass.
- **Daily activity counters stay empty** (`GET /v1/learner/activity`): they are written by the `learner-analytics` stream consumer
  (`stores/learner/admin.py:570` rebuilds them from events); a bare local uvicorn run has no consumer.
- **`POST /v1/learner/register` ignores `Idempotency-Key`** (a replay is a `409` duplicate email, never a replayed `201`).
- **`GET /v1/problems/by-code/{code}` is public and returns `solutions[].body_markdown` and `official_answer`** (content read, outside the learner
  journeys; flagged because the step runtime is built so learners never see step text before earning it).
- Hint level 5 returns the canonical step (`hint_source: REFERENCE_STEP`) by design.

## Harness defects (apitest/*.py outside journeys/, not edited)

1. `Ctx.unique_email()` (`apitest/context.py`) builds `...@example.test`; the API's `EmailStr` rejects the reserved `.test` TLD with `422`, so
   a journey using it cannot register. The learner journeys use their own `new_email()` (`@example.com`).
2. `python -m apitest` writes the server log to `apitest/reports/server-<mode>.log`; concurrent runs (several agents) overwrite each other's log
   (another suite's quiz requests appeared in mine). A per-run log name would fix it.
3. `test-writable` points `content` at `dev` under the write guard, so any runtime path that writes the content table (the hint cache, F1)
   fails with `ReadOnlyViolation` in this mode. Level-1 hints work only because they were cached earlier.
4. `Exchange` has no response-header field, so header assertions (e.g. `Idempotent-Replayed`) must use the raw `httpx.Response` returned by `expect`.
